## Weaknesses

### [BLOCKER] No export or import of Turtle's own database, so all learned listening data is lost on any move

- Evidence: Upstream's backup zip holds only BACKUP_DATABASE_ENTRY and BACKUP_SETTINGS_ENTRY (androidApp/.../backup/BackupRestoreManager.kt:169-176); turtle.db at TurtleDatabase.android.kt:8; turtle/docs/release.md:116-124
- Why it matters: Turtle's value is the profile it learns: play history, feedback, Not interested, artist links, kept shelves. None of it is in the backup a user can make. The only documented transfer is an adb copy between debuggable builds, and a release build is not debuggable, so after 0.1.0 there is no path at all. A new phone or a reinstall silently resets the listener.
- Fix sketch: Add export/import to turtle/bridge/.../SqlitePlayEventStore.kt (a versioned archive of play_event, track_feedback, pref, artist_link, observed_song, shelf_song), reuse PlayEventStore.commit/replaceSource, add the SAF and desktop file-dialog actuals the plan names, and put the entry in ShellSettingsTurtle.kt beside storage and backup.

### [MAJOR] Desktop migration is all-or-nothing per tree, never retries, and has no free-space check

- Evidence: turtle/bridge/.../DesktopDataMigration.kt:130-139 (four trees, data/metrolist as one unit), :147 (any existing destination is skipped), :156-177 (no space precheck; FAILED deletes staging)
- Why it matters: The library database and the offline downloads share one tree (MusicDatabase.desktop.kt:12; DownloadManager.kt:252). A full disk or a kill mid-copy fails the whole tree; Turtle then creates a fresh metrolist.db, the destination exists from then on, and :147 never retries. The listener sees an empty library with nothing on screen explaining it.
- Fix sketch: In DesktopDataMigration.kt: size the source and check usable space on the destination store first; split data/metrolist into a database-plus-settings step and a downloads step so one failure cannot take both; record FAILED in a pref and surface it once in Shell with the retry instructions from release.md:128-132.

### [MAJOR] The migration blocks startup before any window, with no progress and no cancel

- Evidence: turtle/HOOKS.md:94 (#70, first line of desktop main); DesktopDataMigration.kt:97-103, 156-167 (up to COPY_ATTEMPTS = 3 full copies), :215-224 (quick_check over every copied database)
- Why it matters: A listener with a large offline library waits minutes on a black screen on the first start of 0.1.0. If a database check fails the whole tree is copied again, up to three times. A user who assumes it hung and kills the app then lands in the all-or-nothing failure above.
- Fix sketch: Show a minimal Swing progress window from migrateDesktopDataAtStartup (desktopApp/.../Main.kt, hook #70) with per-tree progress, or copy only settings, secrets and the databases before the window opens and move the downloads tree in the background with the app usable.

### [MAJOR] Orphaned migration staging trees are swept only while the destination is absent, and only after an hour

- Evidence: DesktopDataMigration.kt:147 (early return before the sweep), :153 and :317-327 (removeStaleStaging), :85-86 (STALE_STAGING_MS = 1 h)
- Why it matters: A process kill mid-copy leaves a full-size .<name>.turtle-migrating-* tree. Relaunching inside the hour makes a second full copy beside it. Once a later attempt succeeds the destination exists, :147 returns before the sweep, and the orphan is never removed: for a large offline library that is gigabytes of dead files the user will never find.
- Fix sketch: Call removeStaleStaging unconditionally at the top of runAtStartup for all four destination parents, before the per-tree existence check, and shorten the one-hour grace since a staging folder is never shared between processes.

### [MAJOR] The desktop cache tree is abandoned by the folder move: re-downloaded, and the old copy is never cleaned

- Evidence: shared/.../utils/XdgUtils.kt:20-27 (#67 moves the cache home); DesktopDataMigration.kt:130-136 copies data, config and state only; desktopApp/.../utils/DesktopImageLoader.kt:46 and .../storage/SongCacheManager.kt:171
- Why it matters: Cached audio and artwork can be hundreds of megabytes to gigabytes. After the move Turtle re-downloads all of it, costing bandwidth and first-session latency, while the old tree stays in %LOCALAPPDATA%\Metrolist or ~/.cache/metrolist forever. Nothing in the UI mentions either cost.
- Fix sketch: Either add the cache home to DesktopDataMigration.migrate's tree list, which the existing quick_check and atomic-rename machinery already covers, or report the abandoned bytes once in the Storage settings page with an action to delete the old tree.

### [MAJOR] Offline downloads are duplicated rather than moved, permanently doubling disk use

- Evidence: desktopApp/.../storage/DownloadManager.kt:252 (downloads under the data home); DesktopDataMigration.kt:132 (copies data/metrolist), :34 ("never deletes or changes the source")
- Why it matters: Copy-only is right for the database, but applying it to downloads means a listener with a 40 GB offline library needs 80 GB and is never told. Nothing offers to remove the original after a verified copy.
- Fix sketch: Give downloads their own step in DesktopDataMigration.kt that tries an atomic rename within the same store first and copies only as a fallback, and after a COPIED outcome offer deletion of the source from the Storage settings page rather than doing it silently.

### [MAJOR] No CI job compiles Turtle's Android or desktop app, and the Shell UI tests never run in CI

- Evidence: .github/workflows/turtle-engines.yml:29-39 (only ./gradlew -p turtle/engines check); settings.gradle.kts:62-72 (turtle-bridge and turtle-ui are app-build modules, not part of the engines included build); turtle-release.yml:180, 238
- Why it matters: turtle-engines.yml covers four pure-Kotlin engine modules only. :turtle-bridge:desktopTest runs just inside the release workflow at tag time, and :turtle-ui:desktopTest (the headless Shell screenshot tests) runs nowhere. With upstream's ci.yml disabled in the fork, a compile break in the bridge or Shell lands on main and is found while cutting a release.
- Fix sketch: Add jobs to turtle-engines.yml for :turtle-bridge:desktopTest, :turtle-ui:desktopTest and a compile-only :androidApp:compileReleaseKotlin plus :desktopApp:compileKotlinJvm, each in its own job so no two Gradle invocations share a workspace.

### [MAJOR] The release build path has never been executed; the first R8 run on Shell happens during a release

- Evidence: git tag -l is empty; androidApp/build.gradle.kts:293-294 (isMinifyEnabled and isShrinkResources true for release); turtle/docs/plans/2026-11-23-status.md:57 (the device check used app.turtleplayer.debug)
- Why it matters: Every on-device check so far used the debug build, which runs neither R8 nor resource shrinking. Turtle's bridge, engines and Shell resources have never been minified, and androidApp/proguard-rules.pro is 21 lines naming no app.turtleplayer class. The first run is inside turtle-release.yml, where recovery means another versionCode.
- Fix sketch: Before tagging, run :androidApp:assembleRelease once at a throwaway version, install it and walk Home, Search, mix details, Infinity, settings and Updates; add any needed keeps to androidApp/proguard-rules.pro; and archive mapping.txt as a release asset in turtle-release.yml beside the APK.

### [MAJOR] Every desktop install is offered pre-releases, so a release cannot be soft-launched

- Evidence: DesktopUpdateManager.kt:120-121 (availableUpdate has no prerelease filter), :125-131 (findUpdate defaults includePrereleases = true), :60-74 (recovery uses that default); AppUpdateManager.kt:228
- Why it matters: Android's normal check honours isPublishedStable but the desktop check does not, and neither crash path does. There is no way to publish to volunteers first, and release.md:106-110 confirms demoting a release to pre-release does not hide it. The only remedy is turning a published release back into a draft, never drilled.
- Fix sketch: Derive includePrereleases from Settings.shared.updateChannel and apply the same filter in availableUpdate and findUpdate in DesktopUpdateManager.kt, so a Turtle pre-release reaches only installs that opted in; then drill the gh api -F draft=true rollback once before 0.1.0.

### [MAJOR] The signing certificate is not pinned, so the first release can be signed by any key

- Evidence: turtle/release/ contains only identity.android.gradle (no signing-cert.sha256); .github/workflows/turtle-release.yml:258-264 prints ::warning:: and continues when the file is missing
- Why it matters: The pin is the gate that stops a wrong or substituted key from shipping, and Android refuses every future update to an install signed by a different key. It is inactive on exactly the release that fixes the key for the lifetime of the app id.
- Fix sketch: Generate the key offline per release.md:46-52, commit the apksigner SHA-256 digest to turtle/release/signing-cert.sha256 before tagging v0.1.0, and change turtle-release.yml:262-264 from a warning to a hard failure so a missing pin can never ship.

### [MAJOR] The drive log is always on, records track titles every 30 s, and is included in Android cloud backup

- Evidence: turtle/bridge/.../TurtleRuntime.kt:117-120 (DriveLog.start unconditional); TurtleModule.kt:211-212 with HEARTBEAT_MS = 30_000 (:626); DriveLog.android.kt:31; backup_rules.xml and data_extraction_rules.xml exclude no files path
- Why it matters: Up to 6 MB of listening history, Bluetooth device names, audio modes that reveal when the user was on a call, network type and process exit reasons sit in the app's files directory in every release build. Neither backup rules file excludes it, so Auto Backup and device transfer copy it off the device, contradicting DriveLog.kt:17.
- Fix sketch: Exclude turtle-drive.log and turtle-drive.1.log in both backup_rules.xml and data_extraction_rules.xml; gate DriveLog.start on a new key in PreferenceKeys.kt; log the song id without the title in the heartbeat; add a Shell diagnostics entry to view, share and delete the log.

### [MAJOR] Crash reports go to upstream Metrolist's Sentry project and the setting never says so

- Evidence: androidApp/src/release/.../SentryManager.kt:56 and desktopApp/.../utils/SentryManager.kt:129 (one DSN); androidApp/build.gradle.kts:236-237 (org metrolistgroup, project metrolist-kmp); shared/.../composeResources/values/strings.xml:1244
- Why it matters: The switch promises to send crashes, performance data and playback details such as track info "to Sentry" without saying the receiving project belongs to a different project than the app installed. For a fork whose pitch is on-device privacy that is an honest-labelling failure, and the Windows migration carries a consent given in Metrolist over to Turtle.
- Fix sketch: Until Turtle has its own DSN, hide the diagnostics switch through a TurtleUiSlots flag or add a Turtle-specific description naming the receiving project; and have DesktopDataMigration.fixUp drop sentryEnabled from the copied settings.properties as it already drops updateCacheSource (:254-259).

### [MAJOR] The Android baseline profile covers the screens Shell replaced, not Shell

- Evidence: androidApp/src/main/baseline-prof.txt:4-23 (HomeScreenKt, HomeContentKt, SpeedDialGridKt, MiniPlayerKt, shared/ui/player/**); no app/turtleplayer entry; TurtleUi.kt:31-38 and AdaptiveNavigationScaffold.kt:310 replace those surfaces
- Why it matters: Cold start and first scroll are what the profile exists for, and every profiled UI class is one Shell no longer draws. Shell's navigation, Home rows, mix cards and player composables run interpreted until JIT warms them, which is felt most on the low-end phones this app targets.
- Fix sketch: Add HSPLapp/turtleplayer/ui/**->**(**)**, HSPLapp/turtleplayer/bridge/**->**(**)** and the Shell theme and component packages to androidApp/src/main/baseline-prof.txt, or add a macrobenchmark module and generate the profile from a real Shell cold start.

### [MINOR] Most Shell artwork requests ask for whatever resolution the API returned

- Evidence: turtle/ui/.../components/ShellComponents.kt:134-154 (artCandidates returns the bare URL when sizePx is null); 36 of 47 ShellArt call sites in turtle/ui/src pass no sizePx; shared/.../utils/ArtworkUrl.kt:140-143
- Why it matters: Small list rows and grid tiles fetch the same bytes as large art, costing bandwidth and slowing first paint of a long Home or Library list on a slow connection. Upstream already has the sizing helper that would avoid it.
- Fix sketch: Pass a sizePx derived from the composable's own constraints in ShellArt (BoxWithConstraints or onSizeChanged with LocalDensity) so sizedArtworkUrl requests a matching variant, keeping the existing fallback chain for missing sizes.

### [MINOR] Turtle still presents itself as Metrolist to GitHub, Windows and SmartScreen

- Evidence: AppUpdateManager.kt:211 (User-Agent Metrolist/<version>); DesktopUpdateManager.kt:201; turtle-release.yml:327-328 (the packaging task still names the exe and zip entry Metrolist); turtle/docs/release.md:57-58
- Why it matters: A first-time Windows listener extracts Turtle-windows-x64-0.1.0.zip, runs Metrolist.exe, is stopped by SmartScreen on an unsigned binary, and then sees Metrolist in Task Manager. Nothing is broken, but the install says the app is something else.
- Fix sketch: Spend the remaining hook lines on nativeDistributions packageName and the launcher name in desktopApp/build.gradle.kts and packaging-launchers.gradle.kts, change the two User-Agent strings, and decide on a code-signing certificate before a public beta.

### [MINOR] Release-endpoint guard skips turtle/ and iosApp/, and its allowlist is a bare substring

- Why it matters: A new upstream URL added in turtle/ or in iosApp Swift passes unchecked, and any future line whose text contains the allowlisted assignment is exempt wherever it appears. LATEST_RELEASE_URL also lives in commonMain (LatestRelease.kt:8), not iosMain, so the exemption is broader than its comment implies.
- Fix sketch: Add turtle/ and iosApp/ to the grep scope in check-release-endpoints.sh, include *.swift, and anchor the allowlist to the two exact file paths rather than matching the assignment text anywhere in the tree.

### [MINOR] The Android nightly re-fetch still calls upstream's API, guarded only by a manual workflow toggle

- Evidence: AppUpdateManager.kt:123 (NIGHTLY_RELEASE_URL points at MetrolistGroup), :230-233 and :256-259 (nightly offered on the crash path and re-fetched after download); release.md:30-36; nightly.yml:248 creates a nightly release
- Why it matters: If nightly.yml is ever re-enabled in the fork, a nightly release lands in Turtle's own repository, both updaters treat that tag specially, and the re-fetch mixes metadata from a different repository. Mitigation: every nightly.yml job uses blacksmith-* runners (:24, :96, :183), so in a fork without them the jobs never get a runner.
- Fix sketch: Point NIGHTLY_RELEASE_URL at TurtleRelease.RELEASES_API like RELEASES_URL (one more line under hook #64), or make isNightly return false for the nightly tag so the whole nightly path is dead code rather than configuration-dependent.

### [MINOR] Upstream's release workflow fires on the same tag pattern as Turtle's

- Evidence: .github/workflows/release.yml:1-6 (push tags v*.*.*) and turtle-release.yml:9-10 (identical); turtle/docs/release.md:30-36 (a tag check cannot stop it; only disabling the workflow can)
- Why it matters: Pushing v0.1.0 starts both workflows. Mitigation: all eight release.yml jobs use blacksmith-* runners (:22, 267, 400, 440, 480, 502, 516, 559), so in the fork they queue without a runner and cannot publish; but the repository then shows a pending or failed Release run beside every Turtle release, which hides real failures.
- Fix sketch: Add a first step to release.yml's prepare job that exits 0 when turtle/branding.properties exists, recorded as a hook, so the guard survives upstream merges instead of depending on a GitHub setting a new maintainer will not know about.

### [MINOR] On Linux the Discord sign-in desktop entry is written where no desktop environment looks

- Evidence: desktopApp/.../auth/DesktopDiscordRegistration.kt:42 (File(XdgUtils.getXdgDataHome(), "applications/...")) with XdgUtils.kt:11-18 (#67) resolving to ~/.turtleplayer/data; turtle/docs/release.md:137-139
- Why it matters: Hook #67 moved the data home, so the handler file lands in ~/.turtleplayer/data/applications instead of ~/.local/share/applications and Discord sign-in link handling silently stops working. It is a regression Turtle introduced, documented but unfixed, and it blocks taking Linux seriously as a target.
- Fix sketch: Resolve the applications directory from the real XDG_DATA_HOME, or ~/.local/share as its fallback, rather than from XdgUtils.getXdgDataHome() in DesktopDiscordRegistration.kt, since that one path must stay where the desktop environment reads it.

### [MINOR] Turtle's own CI workflow pins no action versions while its release workflow pins every one

- Evidence: .github/workflows/turtle-engines.yml:16, 32-37 (actions/checkout@v4, actions/setup-java@v4, gradle/actions/setup-gradle@v4, actions/upload-artifact@v4) against turtle-release.yml:29, 141, 206, 270, 349 (all pinned to commit SHAs)
- Why it matters: turtle-engines.yml runs the hook-ledger and release-endpoint guards on every push and pull request. A compromised mutable tag in a floating action would execute inside the job that is supposed to enforce Turtle's release invariants.
- Fix sketch: Pin the four actions in turtle-engines.yml and in turtle-upstream-sync.yml to commit SHAs with a version comment, matching the style already used throughout turtle-release.yml.

- Android Auto Backup carries databases/turtle.db because neither rules XML excludes it. Is the backed-up copy consistent when SQLite's WAL (SqlitePlayEventStore.kt:51) has not been checkpointed, and is -wal backed up with it?
