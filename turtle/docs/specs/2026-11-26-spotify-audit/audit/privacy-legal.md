## Weaknesses

### [BLOCKER] Turtle's own history and taste profile are lost on any device move, and sit in Google's backup

- Evidence: turtle.db in the app databases dir (turtle/bridge/src/androidMain/.../TurtleDatabase.android.kt:8); absent from the backup zip (androidApp/.../backup/BackupRestoreManager.kt:155-178); not excluded from cloud backup (androidApp/src/main/res/backup_rules.xml:13)
- Why it matters: A listener who backs up in Settings and restores on a new phone keeps playlists and likes but loses every Turtle play event, Not interested vote, feedback, artist link and kept shelf, so Home and radio start from nothing. The same data does leave the device through Android cloud backup, contradicting .github/README.md:34 and turtle/AGENTS.md:53.
- Fix sketch: Ship roadmap area 5: a turtle.db export/import from Shell. Honest interim: add a turtle.db entry in androidApp/.../backup/BackupRestoreManager.kt (new hook lines, ledger update) and exclude databases/turtle.db plus files/turtle-drive*.log in both androidApp/src/main/res/backup_rules.xml and data_extraction_rules.xml.

### [MAJOR] The sp_dc Spotify scraper is three taps from Shell's Settings, against Turtle's file-only rule

- Evidence: Shell's Backup page (turtle/ui/.../ShellSettingsTurtle.kt:601,722) renders upstream's screen (SettingsScreen.kt:511), whose dialog offers Connect Spotify account (BackupRestoreScreen.kt:958-985) and harvests sp_dc in a WebView (SpotifyLoginScreen.kt:86-97,270-272)
- Why it matters: turtle/AGENTS.md:56 says 'We never scrape Spotify; imports read only files the user downloads themselves'. The shipped app does the opposite: spotlib impersonates Spotify's web player with a hardcoded client id and a reverse-engineered TOTP secret (meow/nyx/spotlib/Config.kt:45-47, Totp.kt:7-8) against open.spotify.com and api-partner.spotify.com.
- Fix sketch: Close three entry points, not one: the provider tile (BackupRestoreScreen.kt:958-985, desktopApp/.../SettingsOverlay.kt:493), the auto-detecting paste path (BackupRestoreScreen.kt:636 and BackupRestoreSettings.kt:497 via UnifiedPlaylistImporter.kt:118) and the silent session restore (BackupRestoreScreen.kt:300-302). Pair it with the compliant replacement.

### [MAJOR] Turtle's compliant file importers have no UI, so only the forbidden path is reachable

- Evidence: SpotifyHistoryImporter and ListenBrainzHistoryImporter are bound (turtle/bridge/.../TurtleModule.kt:112-113) but commitHistoryImport (TurtleRuntime.kt:688) and removeImportedHistory (:700) have no caller outside TurtleRuntimeTest.kt:502,506; no import string exists in turtle/ui
- Why it matters: The strongest privacy code in the repository is dead. A listener arriving from Spotify cannot feed Turtle their own data export, the cold-start fuel, and is instead offered an account connect that hands over a session cookie. This inverts Turtle's stated position and wastes the whole stage, preview and commit engine.
- Fix sketch: Add platform file reading in turtle/bridge androidMain (SAF OpenDocument plus ZipInputStream, counting uncompressed chars per entry against ImportLimits.maxFileChars) and desktopMain (file dialog), then a Shell screen under the Backup group in ShellSettingsTurtle.kt:601,722 that calls stage, shows the ImportPreview counts and commits.

### [MAJOR] Crash reporting can be switched on at first run but never off inside Turtle

- Evidence: Onboarding Yes sets it true (androidApp/.../onboarding/OnboardingScreen.kt:264 -> App.kt:336-340); Shell strips the toggle from Privacy (turtle/ui/.../ShellSettingsTurtle.kt:215,594) and search runs on the filtered registry (ShellSettings.kt:119,291)
- Why it matters: The onboarding page a Turtle listener sees promises 'You can change this anytime in Settings' (shared/.../composeResources/values/strings.xml:3323). In Turtle that promise is false on both platforms, since desktop settings also route through SharedSettingsScreen.kt:171. Consent that cannot be withdrawn is worse than no prompt at all.
- Fix sketch: One choke point: a hook making isCrashReportingAvailable() (shared/.../utils/CrashReporting.kt:5) return false for Turtle. That drops the Android page (OnboardingScreen.kt:91), the desktop page (DesktopOnboarding.kt:114), the Settings item (PrivacySettingsRegistration.kt:144) and closes Sentry at init (SentryManager.kt:49). HIDE_PRIVACY can then go.

### [MAJOR] Crash reports and playback telemetry go to Metrolist's Sentry as a Metrolist release

- Evidence: androidApp/src/release/.../utils/SentryManager.kt:26,56 (release com.metrolist.music.kmp@<version>, Metrolist DSN) and desktopApp/src/jvmMain/.../utils/SentryManager.kt:129; symbol org metrolistgroup, project metrolist-kmp at androidApp/build.gradle.kts:236-237
- Why it matters: If a listener opts in, Turtle sends crashes, ANRs, breadcrumbs and 'playback details such as track info' (strings.xml:1244) plus a playback.video_id tag (PlaybackErrorReporter.kt:49) to a third party Turtle does not control, under a version string that makes them look like Metrolist 0.1.0 crashes. No auth token is set, so they arrive unsymbolicated.
- Fix sketch: Decide with the owner: disable crash reporting via the isCrashReportingAvailable hook above (preferred, it also closes the previous row), or set Turtle's own DSN, release prefix and org/project in androidApp/src/release/.../SentryManager.kt:26,56, desktopApp/.../SentryManager.kt:129 and androidApp/build.gradle.kts:236-237. Record it in turtle/docs/release.md:176-181.

### [MAJOR] Pause listening history does not stop the drive log writing song titles and device names

- Evidence: The heartbeat writes song=<id> <title> every beat with no pause check (turtle/bridge/.../TurtleModule.kt:209-213); audio sinks are logged by product name (turtle/bridge/src/androidMain/.../DriveLog.android.kt:140-144); DriveLog.start is unconditional (TurtleRuntime.kt:120)
- Why it matters: The listener turns on the very control Shell re-describes (ShellSettingsTurtle.kt:583-594) and a plaintext record of what they played keeps growing in files/turtle-drive.log, with Bluetooth product names that are often personal. No setting, no viewer and no clear action exists in Shell, so they cannot even see what was kept.
- Fix sketch: Gate the heartbeat in turtle/bridge/.../TurtleModule.kt:209-213 on listenHistoryPaused() and drop the title from it (the id is enough to diagnose a stall). Add a Shell control under Privacy in ShellSettingsTurtle.kt:585-594 to view, share and clear turtle-drive.log, and exclude it from both Android backup XMLs.

### [MAJOR] The drive log's own promise that nothing leaves the device is false on Android

- Evidence: turtle/bridge/src/commonMain/.../DriveLog.kt:17 states 'Nothing leaves the device'; the file lives in filesDir (DriveLog.android.kt:29-32) and neither backup_rules.xml nor data_extraction_rules.xml excludes it
- Why it matters: With Android backup on (android:allowBackup="true", AndroidManifest.xml:71) the flight recorder is copied off the phone on cloud backup and device transfer. The claim in the code, in turtle/AGENTS.md:53 and in .github/README.md:34 is wrong, and a public promise that does not hold is the one defect that costs a privacy-first product its credibility.
- Fix sketch: Add exclude entries for turtle-drive.log and its .1.log rotation (domain file) and for turtle.db with -wal and -shm (domain database) to androidApp/src/main/res/backup_rules.xml and data_extraction_rules.xml. These are upstream files, so add two HOOKS.md rows against the 85/90 budget.

### [MAJOR] Spotify Canvas can be switched on by a restored preference, with no Shell switch

- Evidence: PlayerViewModel fetches on song change (shared/.../viewmodels/PlayerViewModel.kt:341,352 -> :843 -> :935-947) through DirectCanvasProvider.kt:105; prefs are portable (Settings.kt:413,484,710, absent from nonPortableKeys at :1341-1378); Shell replaces PLAYER_ARTWORK (ShellSettingsTurtle.kt:392-397)

Decide it with the Spotify policy question, since the code path is the same spotlib client as the importer.

### [MAJOR] No way to permanently delete Turtle's listening history, and upstream deletions never reach it

- Evidence: Shell's only history control is the reversible lens (turtle/ui/.../ShellSettingsTurtle.kt:461-466, copy at strings_settings.xml:99); upstream deletes single plays (shared/.../db/daos/HistoryDao.kt:215) but MetrolistHistoryImport runs once and is never re-synced (MetrolistHistoryImport.kt:28,47)
- Why it matters: A listener who deletes an embarrassing play in upstream's History screen (reachable from Android's Home top bar, MetrolistApp.kt:1522-1525, and the desktop destinations card, ShellDesktop.kt:317) still sees it shape Home, radio and Jump back in, because the copy in turtle.db survives. No delete-my-data action exists in Shell.
- Fix sketch: Add a Delete listening history action beside Reset taste in turtle/ui/.../ShellSettingsTurtle.kt:450-466 calling PlayEventStore.deleteSource for LOCAL and each import source through TurtleRuntime, and either observe upstream event deletions in turtle/bridge/.../MetrolistHistoryImport.kt or stop treating upstream's History as authoritative.

### [MAJOR] Turtle ships with no privacy policy, and first run links listeners to Metrolist's

- Evidence: shared/src/commonMain/.../ui/onboarding/OnboardingContent.kt:331 hardcodes https://metrolist.cc/privacy behind 'Read our privacy policy' (:338); no privacy document exists under turtle/, only the internal rule at turtle/AGENTS.md:53
- Why it matters: Turtle ships its own app id (app.turtleplayer), its own binaries and its own data stores, and it keeps things Metrolist's policy never describes: turtle.db play events, the co-listening graph and the drive log. Pointing the listener at another project's policy is inaccurate and unfair to Metrolist, who would field the questions.
- Fix sketch: Write turtle/docs/privacy.md covering turtle.db, turtle-drive.log, what the taste engine keeps, what pause and reset do and which integrations are opt-in; publish it with the repository; point the onboarding link and a Shell Privacy row at it (one hook line at OnboardingContent.kt:331 plus an item in ShellSettingsTurtle.kt:585-594).

### [MAJOR] About omits the GPL copyright and no-warranty notices and offers Metrolist's source, not Turtle's

Add the three strings to turtle/ui/src/commonMain/composeResources/values/strings_settings.xml.

Better: drop the flow and clear any stored spotifySession once at startup from turtle/bridge, so existing test installs stop holding a live credential.

## Strengths

- **The file-based Spotify importer refuses to read the identifiers the export hands it** — turtle/engines/events/src/commonMain/kotlin/app/turtleplayer/events/imports/SpotifyHistoryImporter.kt:28-32 and :60-63: track URIs, platform, country, IP address and offline flags are never parsed, and incognito_mode rows are excluded unless the listener asks | beats Spotify: Spotify's own export carries IP address, platform and country per play. Turtle's parser is written so those fields never enter its store, and private-session plays stay out by default.
- **Imports are a preview and an explicit commit, so a bad file cannot destroy existing history** — Stage then commit at turtle/engines/events/.../imports/HistoryImport.kt:56-60,221 and turtle/bridge/.../TurtleRuntime.kt:688; one SQLite transaction per source at turtle/bridge/.../SqlitePlayEventStore.kt:288-303; bounds at HistoryImport.kt:28-52

Turtle's pause is a persistent setting that also stops the recommender learning from radio pages and saves, not only the visible history.
- **Taste reset is reversible and says so plainly instead of implying deletion** — turtle/ui/src/commonMain/composeResources/values/strings_settings.xml:99-103 ('Nothing is deleted, so you can undo it', plus what is and is not kept), wired at turtle/ui/.../ShellSettingsTurtle.kt:383-386,461-466
