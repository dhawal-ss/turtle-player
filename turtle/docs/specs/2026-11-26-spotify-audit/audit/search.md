## Weaknesses

### [BLOCKER] Local and offline results bypass every content block (hide explicit, blocked artists, Not interested)

- Evidence: ShellSearch.kt:208-219 renders the bridge page raw; TurtleSearch.kt:49-101 never calls BlockedContent; the view model filters only its own online page (SearchViewModel.kt:187,549-556). grep BlockedContent in turtle/bridge finds Home, Explore and radio, never search.
- Why it matters: The most dangerous defect here. With 'Hide explicit' on, explicit songs appear on the first paint of every search and in every offline search. Songs marked Not interested, blocked artists, podcasts with 'hide podcasts' on, video songs and short songs all come back. A user who curated blocks sees the app ignore them, only in Turtle's own path.
- Fix sketch: Filter in the bridge, not the UI, so every consumer is covered: in turtle/bridge/.../TurtleSearch.kt wrap the mapped song/artist/album lists (lines 84-86) with BlockedContent.filterItems(..., snapshot) taken once per rerank, and re-run on BlockedContent.version as UpstreamBlocks.kt:50 does. Add a test beside TurtleSearchTest.kt.

### [BLOCKER] Offline, the local page offers songs that are not downloaded and cannot play

- Evidence: LibrarySync.kt:56-67 indexes every song-table row (library plus anything ever played) with no download check; upstream restricts offline results to local, downloaded or cached rows (OfflineMedia.kt:18, YouTubeRepository.kt:1551-1553), and Shell replaces that page (ShellSearch.kt:217).
- Why it matters: On a plane or underground, the user searches, taps a row labelled 'From your library' and playback fails. Upstream got this right and Turtle's takeover regressed it, exactly when the listener has no alternative.
- Fix sketch: Pass the available set into the local stage: give TurtleRuntime.searchLocal (TurtleRuntime.kt:431-441) the OfflineSongAvailability ids (same source as YouTubeRepository.kt:2518) and filter the mapped songs in TurtleSearch.local, or index a downloaded/cached flag in LibrarySync.kt:57. Apply it only while PlaybackNetworkStateStore reports disconnected.

### [MAJOR] Offline search loses playlists, albums and artists entirely

- Evidence: TurtleSearch.local can return only songs: artistOf/albumOf need a browseId the local index lacks and an online list that is empty (TurtleSearch.kt:67-68,85-86,104-108). Shell still prefers it offline (ShellSearch.kt:217) over upstream's page, which has playlists (OfflineMedia.kt:118-124).
- Why it matters: Offline, 'gym' no longer finds the user's own 'Gym' playlist, and an artist name returns a song list instead of the artist. Spotify's offline search finds playlists, albums and artists instantly, so this is a step back from both Spotify and upstream Metrolist.
- Fix sketch: Two parts. (1) In TurtleSearch.kt have local() accept upstream's offline page and pass its playlist, album and artist sections through, as rerank already does for playlists (line 96). (2) Index playlists: add DocType.PLAYLIST (LexicalScoring.kt:10) and feed names from the playlist table in LibrarySync.kt so playlist names get typo tolerance.

### [MAJOR] The 'Retry' chip after a failed page load does nothing

- Evidence: ShellSearch.kt:356-366 calls slot.onLoadMore() while loadMoreFailed is true; the host binds it to loadMoreFilteredResults (androidApp/.../SearchScreen.kt:545), which returns early since canLoadMoreFilteredResults needs !loadMoreFailed (SearchViewModel.kt:718-727).
- Why it matters: A dead button at the bottom of a filtered result list. Once paging fails the only escape is changing the query or filter; tapping Retry does nothing and the spinner never returns. The flag is cleared only by retryLoadMoreFilteredResults (:254) or a query change (:682-689), and the former is not in SearchSlot.
- Fix sketch: Add onRetryLoadMore to SearchSlot (shared/.../turtle/TurtleUiSlots.kt:116-135), pass it at the hook site (shared/.../ui/screens/SearchScreen.kt:133) and call it from the retry chip in ShellSearch.kt:360. One line in each of three files.

### [MAJOR] Non-English content language gets duplicated song, artist and album sections

- Evidence: TurtleSearch.kt:90-96 drops upstream sections whose title is in setOf("Songs","Artists","Albums") (:131-134); YouTube's shelf titles come straight from the response and are localized (YouTubeSearchOperations.kt:159-184; typeLabel at :186-213 is response text too).
- Why it matters: A Spanish or Japanese listener sees YouTube's 'Canciones' shelf AND Turtle's re-ranked 'Songs' shelf with the same songs listed twice (Shell de-duplicates within a section, not across them: ShellSearch.kt:203,219). It also breaks CLAUDE.md's no-hardcoded-English rule, as the comment at TurtleSearch.kt:131 admits.
- Fix sketch: Stop matching on titles. Tag Turtle's own sections structurally (a kind or replaced flag on SearchSummary in shared/.../model/Models.kt), or drop every upstream section whose items are all SongItem/ArtistItem/AlbumItem, which is what the engine actually ranked, instead of comparing title strings.

### [MAJOR] No local results and no suggestions while typing; nothing at all offline until Enter

- Evidence: Shell runs the local stage only once the query is submitted (ShellSearch.kt:208-212, guarded by s.isQuerySubmitted); while typing it shows only network suggestions, needing 2+ characters and a connection (SearchViewModel.kt:108-124). The engine is built for per-keystroke use (SearchEngine.kt:96-99).
- Why it matters: Spotify answers from the device on the first keystroke. Turtle has a 30 ms local budget and a whole suggester written for this (Suggestions.kt:120-197) and uses neither: offline, typing shows an empty screen; online, there is a visible wait before anything appears.
- Fix sketch: Wire the suggester: build SearchSuggester in turtle/bridge/.../TurtleModule.kt:117-136 over the existing LocalLibrary, PlayEventStore and a SearchHistory backed by Settings.shared.searchHistory, expose suggest(query) on TurtleBridge beside searchLocal (TurtleModule.kt:296-304), and render its rows above the online ones in ShellSearch.kt:311-320.

### [MAJOR] Lyrics search can never match: nothing ever fills the lyrics index

- Evidence: grep for putLyrics or LyricsIndex outside turtle/engines/search returns nothing, so LocalLibrary.putLyrics (SearchEngine.kt:44) has no caller; the engine still queries the empty index on every 3+ token query (SearchEngine.kt:171-179). Lyrics are cached at shared/.../daos/CacheDao.kt:37-43,94.
- Why it matters: 'Find the song from a line I remember' is one of the few things search can do that Spotify also does poorly, and Turtle has the harder half built (two-line windows, typo tolerance, in-order alignment) but ships it dead. The no-results hint even says 'Check the spelling, try fewer words' (strings_search.xml:8).
- Fix sketch: In turtle/bridge/.../LibrarySync.kt, after the song diff (lines 60-67), read cached lyrics for the indexed keys via CacheDao.cachedLyricsIds/cachedLyrics and call library.putLyrics for those present, removing with removeLyrics when a song leaves. Then surface SearchResults.lyrics as a 'matched in lyrics' line on the row in ShellSearch.kt:589-637.

### [MAJOR] Taste controls do not reach search ranking: mutes, likes and 'less like this' are ignored

- Evidence: TurtleSearch.kt:44 uses HistoryAffinityProvider (raw play counts, Providers.kt:94-135) as the engine's AffinityProvider; the taste engine holds mutedArtists, mutedClusters, boosts and dismissals (turtle/engines/taste/.../UserControls.kt:33-62, TasteState.kt:25-31), which search never reads.
- Why it matters: A listener who muted an artist still gets them ranked up in search because they played them last year, and a liked song gets no boost beyond its play count. The app teaches the user these controls work (they do on Home and radio) and then ignores them where the user is explicitly asking for something.
- Fix sketch: Implement AffinityProvider on top of the taste profile in turtle/bridge (beside TasteHistoryLens.kt), returning 0 or a negative version adjustment for muted artists and clusters and blending liked and replayed signals, then pass it instead of HistoryAffinityProvider at TurtleSearch.kt:44,60. Add golden PERSONAL rows asserting a muted artist sinks.

### [MAJOR] Mood and vibe queries are plain text search; one shipped chip parses as a lyrics query

- Evidence: TurtleSearch.kt:69-74 returns null for a MixResult so the mix top is discarded; chips call slot.onSearch (ShellSearch.kt:492-497). The chip 'focus, no lyrics' (shell_vibe_4) ends in 'lyrics', a LYRICS cue word, so QueryParser.kt:319-329,423-427 classifies it over tokens [focus, no].
- Why it matters: The idle screen promises mood entry points ('rainy night indie', 'gym hype', 'sunday slow', 'focus, no lyrics') and delivers a keyword search. The last chip is worse than neutral: LYRICS intent turns off coverage scaling of online rank evidence (ResultMerger.kt:465-469) and scores every track without lyrics at 0.2 agreement, so the order is near-arbitrary.
- Fix sketch: Point the chips at the Infinity Mix (comparison doc win #2): give the MOOD path a bridge route that seeds Infinity from MixSeed instead of dropping it (TurtleSearch.kt:69-74 plus a TurtleBridge entry) and open that mix from ShellSearch.kt:492-497. Separately, treat 'lyrics' as a cue only as a leading word or when the other tokens are not mood or filler words (QueryParser.kt:319-329).

### [MAJOR] Intent rules, mood vocabulary and version filters are English-only

- Evidence: QueryParser.kt:206-213 version words, :270-291 moods/activities/genres/filler, :353 'by', :423-427 cues album/ep/lp/lyrics/song/track, :432-437 function words. All literal English. CLAUDE.md forbids hardcoded English defaults.
- Why it matters: A German user typing 'live' gets the filter but 'livemitschnitt' nothing; 'canciones de entrenamiento' is not a mood query; 'x von y' is not song-by-artist. Half of Turtle's query understanding silently switches off outside English while the UI is fully translated.
- Fix sketch: Move the vocabularies out of code into per-locale resources (a values*/search_lexicon.xml or a bundled table keyed by a language derived from composeResources/values*/ as CLAUDE.md requires), load the set for the content language resolved from Settings (SYSTEM -> JVM locale), and keep English as one locale among others, not the fallback. Add golden rows in a non-English locale.

### [MAJOR] In-library search is a plain substring match while the typo-tolerant index sits unused

- Evidence: Library filtering goes through filterForLibrarySearch -> searchableText().contains(term, ignoreCase = true) (shared/.../model/PlaylistSongSorting.kt:175-178, used ShellLibrary.kt:1303); the desktop sidebar filter is the same (ShellDesktop.kt:441-443). LexicalIndex already holds these songs.
- Why it matters: The same app answers 'beyonce' in catalog search and fails in the library panel; 'acdc' and 'rem' fail; one typo fails; 'Jose' misses 'Jose' with an accent. Users do not model two search engines in one app, they conclude search is unreliable.
- Fix sketch: Expose a library-scoped query on the bridge (add an ids-only variant beside TurtleBridge.searchLocal) and use it to decide membership in prepareShellLibrary (ShellLibrary.kt:1296-1317) and ShellDesktop.kt:441-443, falling back to the substring filter until LibrarySync.isReady(). Keep the existing sort order.

### [MAJOR] Filtered and unfiltered offline searches disagree because they use different engines

- Evidence: Unfiltered offline shows Turtle's engine page (ShellSearch.kt:217); selecting a filter goes to upstream's SQL substring fallback (YouTubeRepository.kt:1641-1655 via SearchViewModel.kt:204-235), which has no typo tolerance or normalization.
- Why it matters: Offline, 'yellw' finds Yellow on the Top tab and nothing under the Songs chip. Narrowing by filter should never make results disappear; it reads as a bug to anyone who tries it.
- Fix sketch: Route the offline filtered path through the same engine: have the bridge answer a filtered local query (TurtleSearch.local plus a kind filter, which LexicalIndex.search already supports through its types parameter, LexicalIndex.kt:133) and use it in ShellSearch.kt:352-367 while the device is offline, as the unfiltered path does.

### [MINOR] No play, shuffle or radio affordance on artist, album or playlist results

- Evidence: ShellSearch.kt:584 shows the play button only for a SongItem, and the card row does the same (:667). onAlbumPlay and onShuffleClick exist upstream (shared/.../SearchScreen.kt:122-123,131; androidApp/.../SearchScreen.kt:516-519,568-577) but are not in SearchSlot (TurtleUiSlots.kt:116-135).
- Why it matters: Searching an artist to start playing is one of the most common search intents, and the top-result card for an artist has no way to start music: the user must open the artist page first. Spotify puts a play button on the top result whatever it is.
- Fix sketch: Add onAlbumPlay and onShuffleClick (or a radio action) to SearchSlot, pass them at the hook site (shared/.../ui/screens/SearchScreen.kt:133), and render HoverPlayButton for ArtistItem, AlbumItem and PlaylistItem in TopResultCard (ShellSearch.kt:583-585) and CardRow (:665-668).

### [MINOR] Song sections are capped at six rows with no way to see more

- Evidence: ShellSearch.kt:394-402 takes 6 items from every all-songs section; the engine keeps 20 (GroupLimits, ResultMerger.kt:49) and upstream's page has more. The only route to more songs is the Songs filter chip, which re-queries the network.
- Why it matters: The seventh-best match is unreachable without a second request, and offline it is unreachable at all because the local page is replaced wholesale rather than paged.
- Fix sketch: Add a 'See all' row under a truncated song section in ShellSearch.kt:394-402 that calls slot.onFilterSelected(SearchFilter.SONG), or expand in place to the section's real size. Reuse the shell_browse_see_all pattern already at :271-284.

### [MINOR] The now-playing row is marked only by colour and an unlabelled animation

- Evidence: ShellSearch.kt:612 colours the title with c.accent when playing and :623-626 adds Equalizer, which has no semantics at all (turtle/ui/.../components/ShellComponents.kt:184-192: three animated boxes, no contentDescription).
- Why it matters: A screen-reader user cannot tell which result is playing, and someone who cannot distinguish the accent colour gets only a small animation. Everything else here is labelled carefully (skeleton :517, explicit tag :617, remove-history :487), which makes this the odd gap.
- Fix sketch: Give Equalizer an optional label parameter and set a 'Playing' content description on the row or the equalizer in ShellSearch.kt:623-626, with a new string in turtle/ui/.../values/strings_search.xml. Apply the same to the compact rows beside the top result.

### [MINOR] Re-ranking adds up to 800 ms to every online search and the local stage has no deadline

- Evidence: TurtleSearch.kt:61 wraps the engine in withTimeoutOrNull(RERANK_TIMEOUT_MS = 800, :135); the local stage runs with deadline = null (SearchEngine.kt:118-121), so only that outer timeout bounds it. The hook runs inside getSearchSummary (YouTubeRepository.kt:1572), on the critical path.
- Why it matters: On a large library the fuzzy term scan is the slowest part (a typo'd 8+ character token scans every longer length bucket, TermMatching.kt:188-196). When the budget is blown the user waits 800 ms and still gets upstream's unranked page, with no sign anything happened.
- Fix sketch: Give the local stage a real deadline in SearchConfig and pass it at SearchEngine.kt:119 so a slow scan degrades instead of eating the whole budget, and log the rerank duration beside the existing TurtleLog.info at TurtleSearch.kt:99. Capping candidates per query token in LexicalIndex.search is the cheap version.

### [MINOR] The user is never told a result matched loosely, and there is no 'did you mean'

- Evidence: The engine records why each result matched (MatchReason/FieldMatch with MatchKind EXACT..INFIX, SearchResults.kt:19-29, LexicalScoring.kt:53-61) and Shell discards all of it; the no-results message only advises checking the spelling (ShellSearch.kt:347-351, strings_search.xml:7-8).
- Why it matters: When typo tolerance saves a query the user learns nothing, and when it fails they get a dead end instead of the correction the index could offer (the lexicons already return the nearest known name with a quality score, LexicalIndex.kt:184-227).
- Fix sketch: On the no-results screen ask the bridge for the best lexicon name match and offer it as a chip ('Did you mean X?') beside the vibe chips in ShellSearch.kt:347-351, exposing it from TurtleSearch via SearchEngine.parse and the LexicalIndex lexicons. Optionally show a quiet 'matched X' note on fuzzy rows.

### [MINOR] 'Hide "From recent searches"' is a setting with no effect in Shell

- Evidence: The toggle is reachable (PrivacySettingsRegistration.kt:102-106, kept by ShellSettingsTurtle.kt:215,584-599) and its string promises to hide that shelf (shared/.../values/strings.xml:649), but Shell never renders uiState.recentSearchItems (no reference in ShellSearch.kt).
- Why it matters: A privacy toggle that does nothing is worse than a missing one: the user cannot tell whether it worked, and if the shelf is later added without the gate the setting stays silently broken.
- Fix sketch: Add the shelf and honour the gate in one change: render recentSearchItems on the idle screen only when !Settings.shared.hideRecentSearches, mirroring SearchContent.kt:286, and wire remove and clear through two new SearchSlot callbacks.

### [MINOR] No way to clear all recent searches from the search screen

- Evidence: SearchViewModel.clearSearchHistory exists (:419-446) and the hosts pass onClearHistory (MobileApp.kt:1223, androidApp/.../SearchScreen.kt:539), but SearchSlot carries only onRemoveHistoryItem (TurtleUiSlots.kt:116-135) and Shell shows a per-row cross only (ShellSearch.kt:487).
- Why it matters: Clearing a long history means eight taps, or finding the action buried in Settings then Privacy. Spotify, YouTube Music and Google all put 'Clear' next to the Recent searches heading.
- Fix sketch: Add onClearHistory to SearchSlot, pass it at the hook site, and put a text action beside the 'Recent searches' heading in ShellSearch.kt:264 with a confirm, reusing the shared clear_search_history strings.

### [MINOR] Swipe actions on search result rows are lost under Shell

- Evidence: The host wraps every SongItem in SongSwipeActions through itemContainer (shared/.../MobileApp.kt:1161-1164) and upstream's content applies it; SearchSlot carries no itemContainer (TurtleUiSlots.kt:116-135) and Shell builds its own rows (ShellSearch.kt:589-637).
- Why it matters: Save or enqueue by swipe works elsewhere in the host app but not in Shell's search, so a gesture learned in the library silently does nothing here. Long-press is the only shortcut Shell offers.
- Fix sketch: Add itemContainer: (@Composable (YTItem, @Composable () -> Unit) -> Unit)? to SearchSlot, pass the host's value at shared/.../ui/screens/SearchScreen.kt:133, and wrap ResultRow's content with it in ShellSearch.kt:589-637, defaulting to a pass-through so desktop and tests are unaffected.

## Strengths

- **A real retrieval engine, not a LIKE query: bit-parallel typo tolerance with a maintained gate** — BitParallelMatcher.kt:34-88 (Myers/Hyyro OSA distance, 64-char patterns), TermMatching.kt:37-115 quality bands, charSignature prefilter :141-152; 96 golden queries in 12 categories with a 2% CI regression gate (golden/GoldenQuerySetTest.kt:88-125, GoldenQueries.kt:27-149) | beats Spotify: Typo tolerance runs on the device against the user's own library, so it works with no connection, and any listener-visible ranking change must pass a committed query set to merge. Spotify's spelling correction is server-side and unavailable offline.
- **The same song from five uploads collapses into one row** — ResultMerger.kt:193-234 union-find over key, ISRC, YouTube id and canonical title plus artist; representative official > in library > popular (:238-244); other uploads kept as alternates (:304); channel decorations stripped (:506-514); cover and karaoke penalised (:308-316) | beats Spotify: Solves a problem specific to a YouTube-backed client, and better than YouTube Music itself, which lists the official audio, the video, a sped-up edit and two re-uploads as separate results.
- **Explicit and clean versions stay distinguishable instead of being merged away** — ResultMerger.kt:210-218 keys the name-based merge on the group's explicit flag so a clean copy can never bridge into an explicit upload; Shell tags the row (ShellSearch.kt:616-619) with the shared 'explicit' string | beats Spotify: The merge is deliberately conservative where a mistake would be invisible and harmful: hiding explicit content must not delete a whole result row.
- **Ranked by what this listener actually plays, on the device, with no ads or promoted placements** — Providers.kt:99-135 play-count affinity over Turtle's own event log with quick skips excluded; weights ResultMerger.kt:12-45 (affinity 0.14, popularity only 0.05, library +0.04, history +0.03); a per-result ScoreBreakdown is kept (SearchResults.kt:31-43) | beats Spotify: No part of the order can be bought, and every component of a result's score is recorded for inspection. Nothing leaves the device for ranking.
- **Text normalization that treats non-Latin and stylised names as first-class** — TextNormalizer.kt:27-66: Cyrillic and kana transliterated, Indic vowel signs preserved while other marks drop, full-width folded, 'P!nk', 'Ke$ha', '&' and '+' as 'and', unspaced scripts indexed per character; ResultMerger.kt:465-503 keeps rank evidence across scripts | beats Spotify: A romaji query can reach a kanji title, and a cross-script result is not punished for sharing no words, which matters for exactly the catalogues a YouTube-backed client is strongest in.
- **Honest labelling of where a result came from** — ShellSearch.kt:329-336 shows 'From your library' (strings_browse.xml:6) whenever the shown page is the local one; TurtleSearch.kt:98-99 logs which side won the top slot; upstream's top is kept when it is a playlist named like the query (TurtleSearch.kt:76-83) | beats Spotify: The app says when it is answering from the device rather than the catalogue, and refuses to steal the top slot from a better upstream match. Neither Spotify nor YouTube Music tells you which engine answered.
- **Staged retrieval degrades instead of failing** — SearchEngine.kt:100-169: stages run in parallel with their own deadlines, each emission updates the result set, every stage's status is reported, and a failed or timed-out stage is recorded rather than thrown; TurtleRuntime.kt:444-452 keeps upstream's page when re-ranking fails | beats Spotify: A slow network degrades to library results rather than a spinner, and every Turtle code path on this screen fails open to upstream behaviour.
- **Query understanding is a replaceable component with an explicit confidence** — IntentClassifier is a fun interface (QueryParser.kt:151-154) with the rule-based v1 behind it; confidence scales how much intent may move the ranking (ResultMerger.kt:479 blend, :142-155 topIntentSlack); intentScores are exposed on every result set (SearchResults.kt:97) | beats Spotify: Uncertainty is propagated rather than hidden: when the parser is unsure, intent stops steering the order instead of guessing confidently.
- **No hardcoded user-facing text in the search UI** — Every label in ShellSearch.kt comes from a resource (imports :83-132; strings_search.xml, strings_browse.xml); section titles map YouTube's English category names onto localized Shell strings (ShellSearch.kt:537-547) | beats Spotify: Keeps the project's own translation rule (CLAUDE.md), so the screen is fully translatable through Weblate. The gap is the engine's internal vocabularies, not the UI.

## Open questions

- Does the local stage stay inside its budget on a real library? LexicalIndex.search has no deadline (SearchEngine.kt:118-121) and the only bound is the 800 ms rerank timeout (TurtleSearch.kt:135). Needs a device timing run; no build was allowed here.
- Are local-file songs (song.isLocal) playable from Shell search results? SongItemMapping.kt:11-23 always sets youtubeId = id and SongCache holds them, so they index and resolve, but the play path for a local id was not traced.
- Does YouTube return localized search shelf titles for every content language, or does WEB_REMIX sometimes answer in English anyway? That decides how often the duplicate-section bug (TurtleSearch.kt:90-96) fires.
- Is the engine's single-CJK-ideograph online trigger (SearchEngine.kt:109,157) ever exercised? In TurtleSearch the online stage reads an already-fetched page (PAGE_CONFIG minOnlineChars = 1), so the rule may be dead in practice.
- Should the local page be merged with upstream's offline SQL page or replace it? Merging fixes playlists and block filtering at once but can show one song twice under two matching rules.
- Are the English vibe-chip strings (shell_vibe_1..4) meant to be translated? If Weblate localizes them, the MOOD lexicon (QueryParser.kt:270-291) will not recognize the result.
- Should search ranking honour taste mutes, given that search is an explicit request? Spotify does not hide a muted artist you searched by name; sinking rather than hiding is probably right, but it is an owner decision.
