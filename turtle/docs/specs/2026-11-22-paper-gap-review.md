STRATEGIC LESSON
The paper's main claim is that Spotify wins with "a coherent system", not one better algorithm. Each listening intention gets its own surface with its own objective, and every surface is placed where the listener will reach it. Its measurement section adds that discovery has to be measured by lasting interest, not by volume. Turtle's main gap is integration, not algorithms. Many engine pieces are finished but never reach a listener: the SearchSuggester, the LyricsIndex, the Spotify and ListenBrainz importers, the typed per-item Reasons, VersionTag, the cluster mute and boost controls, profile(), and the search alternates. Meanwhile, the quality gate measures only the Up Next ranking, a surface listeners never browse as a list. One "will it finish" ranker serves every shelf, and a single finished play counts as a discovery win. The highest-leverage work this session is to wire the built pieces into surfaces (W5, W4, why-this-song, taste controls), to give each surface its own objective, and to make the gate measure what listeners see: shelf overlap, day-over-day freshness and retained discoveries. That way each new piece adds to one coherent system instead of another component that nobody sees.

## Confirmed gaps

### cross-shelf-dedup (rec-surfaces, improvement, M, value high, hooks 0, roadmap new)

**The same songs repeat across Made for you shelves**

- Paper: 2.4: surfaces have different jobs. Pillar 3: diversity. 2.4: optimizing every surface the same way 'risks repeating the same safe songs'.
- Evidence: Confirmed in engines/taste/src/commonMain/kotlin/app/turtleplayer/taste/TasteEngine.kt. homeShelves (~:444-451) builds each shelf on its own: Daily, More like, On repeat, Weekly, Fresh, Rediscover. The final filter visibleLocked (:474-475) only drops empty or suppressed shelves. compose() (:786-798) passes emptyList() history and a fresh RecentlyRecommended(1), so it never sees other shelves. Only artistMixesLocked keeps a `used` set (:856, :882), and only between artist mixes. clusterMixesLocked (:887-903) has no exclusion. moreLikeLocked (:932-955) excludes only the seed track. vectorWeeklyRankedLocked (:958-961) uses discoveryCollector (onboarding, cluster and CF, :116) filtered by !hasHeard, so it can share never-heard picks with the discovery slots of Daily Mix (clusterGen and cfForMix) and of More like X (sessionGen and cfForSeed). Daily Mix familiar slots come from favoritesGen. Without vectors they come from LibraryGenerator. Neither excludes On repeat's tracks (onRepeatLocked :986-1006). The bridge does not dedup Turtle shelves against each other. bridge/src/commonMain/kotlin/app/turtleplayer/bridge/HomeLayout.kt:157 only does distinctBy on the shelf key. Its grid and YouTube-row dedup (:201, :222) does not touch Turtle mixes. One correction to the claim: among cluster Daily Mixes, overlap is weaker than stated. Each mix runs with mixProfile = one cluster (:892). FavoritesGenerator (Generators.kt:126-145) and TasteClusterGenerator (Generators.kt:92-122) then draw familiar tracks only from that cluster's members. So mix-to-mix overlap can come only from embedding neighbours or CF picks near different centroids. It is not systematic.
- Proposal: Engine change in TasteEngine.homeShelves. Build shelves in an ownership order and pass a running exclusion set into each GenerationRequest.exclude and compose(). Weekly Discovery owns its never-heard picks for the week, including when kept from an earlier day, so read them from the stable map before building the daily shelves. Fresh owns new releases. Daily Mixes, then More like X, may use only discovery tracks not already claimed. Familiar overlap is capped: a Daily Mix may not open with On repeat's top tracks, and at most N shared familiar tracks per pair. Cluster mixes get the used set and partition that artist mixes already have. Result: each card in Made for you plays different music.
- Risk: Thinner shelves for light listeners. Keep the minFallbackShelfSize floor (TasteConfig :51) and relax only the familiar cap, never the discovery exclusion. Exclusion order must stay stable across days so kept shelves do not shift (W2 anti-goal: rows that jump around). The offline replay is unaffected because it measures recommendations(), so add a cross-shelf overlap metric under W12.
- Verifier notes: The gap is real across shelf kinds: Daily Mix vs Weekly Discovery, Daily Mix vs More like X, and Daily Mix familiar slots vs On repeat. It is weaker among cluster Daily Mixes themselves. The specs and plans do not mention cross-shelf dedup. W1's dedup covers only the grid, Jump back in and YouTube rows. W2 kept shelves complicate the fix. DAILY, DAILY_MORE_LIKE and WEEKLY are kept per period by stableLocked/keptLocked (:490-500), so the exclusion order must not change already-kept shelves. Reading Weekly's kept picks first, as the proposal says, fits that. The fix belongs to the engine, so it needs no upstream hook. It does not conflict with rejected features: this is diversity within Home, not multiple queues.

### surface-objectives (rec-surfaces, improvement, M, value high, hooks 0, roadmap new (W10's learned ranker later replaces the hand weights; this gives W10 per-surface targets))

**Every surface uses one 'will it finish' ranker; Weekly Discovery favours new songs by known artists**

- Paper: 2.1 and 2.4: Discover Weekly and Daily Mix have different objectives. 11.1: 'Reward the system for helping listeners discover new artists, not only for maximizing immediate plays.' Pillar 3: avoid optimizing only for plays.
- Evidence: The core claim is confirmed. TasteEngine.kt:81 injects a single `ranker: Ranker = HandTunedRanker()`. rankLocked (TasteEngine.kt:770-779) scores every candidate with that one ranker, whatever the shelf. Ranker.kt:5-15 documents the score as P(completed, not skipped). DEFAULT_WEIGHTS gives ARTIST_AFFINITY 0.8 (Ranker.kt:57) and ARTIST_HEARD_BEFORE 0.2 (Ranker.kt:59). On the vector path, Weekly Discovery (vectorWeeklyRankedLocked, TasteEngine.kt:958-961) filters out heard tracks only, not heard artists. weeklyDiscoveryLocked then composes the result as is (TasteEngine.kt:970-971, familiarShare 0.0). SlotKind comes from track HEARD_BEFORE (Ranker.kt:107), so an unheard deep cut by a favourite artist counts as a 'discovery' slot. The generators behind discoveryCollector (TasteEngine.kt:116: onboarding, cluster, CF) do not filter out known artists either (Generators.kt:92-205). Only the no-vector fallback partitions newArtists first (TasteEngine.kt:975-976).

The secondary parts are weaker. Fresh for You's candidates all come from FreshReleaseGenerator, which already admits only recent releases by wanted artists (Generators.kt:206-224). Raising the FRESHNESS weight would therefore only reorder within an all-fresh pool, a marginal change. Rediscover candidates are all already 60 or more days unplayed (Generators.kt:230-243), and the generator sorts them by affinity. DAYS_SINCE_PLAYED having weight 0 (Ranker.kt:89) is true, but the effect is minor.
- Proposal: Engine: add a SurfaceObjective per ShelfKind, a small weight-override map plus a constraint, applied in rankLocked/compose. WEEKLY_DISCOVERY sets ARTIST_HEARD_BEFORE and ARTIST_AFFINITY negative or zero, keeps CLUSTER_SIM and LONG_TERM_SIM as the relevance anchor, and requires at least 50% of items from never-heard artists, matching the existing fallback partition. FRESH_FOR_YOU raises FRESHNESS. REDISCOVER rewards DAYS_SINCE_PLAYED. DAILY_MIX keeps today's weights. UP_NEXT and RADIO stay unchanged. Users see Weekly Discovery introduce artists rather than deep cuts from favourites.
- Risk: Discovery quality may drop if relevance weights are cut too far. Keep the taste-similarity terms. Must pass the 2% replay gate (AGENTS.md); the replay measures recommendations(), so add a per-surface replay under W12 to judge Weekly Discovery.
- Verifier notes: The gap that matters is Weekly Discovery's lack of artist novelty on the vector path. The engine pays favourite-artist affinity for candidates on that shelf, so it fills with unheard tracks by artists the listener already plays. That contradicts the spec's 'Discovery is the week's, like Discover Weekly' goal (spec line 54) and paper section 11.1. The no-vector fallback already encodes the intended new-artists-first behaviour (TasteEngine.kt:975), so the smallest change is in turtle/ and needs no hooks. The engine would apply the same never-heard-artist partition, or a minimum share, on the vector path as well. A per-ShelfKind weight-override map is optional on top of that.

The spec does not plan per-surface objectives. W10 (spec line 104) plans only a learned ranker and better vectors. I found no conflict with the rejected features or with spec decisions. The Fresh and Rediscover weight changes are low value and could be dropped from the proposal. The risk note stands: the 2% replay gate measures recommendations(), so judging Weekly Discovery needs a per-surface eval (W12).

### fresh-coverage-followed (rec-surfaces, bug, S, value high, hooks 0, roadmap new (onboarding-artist ordering becomes a W4 dependency))

**Release Radar only ever scans the top 15 artists and ignores followed artists**

- Paper: 2.4: Release Radar should 'Surface releases from followed and relevant artists'. 11.1: artist follows as a signal.
- Evidence: Confirmed in code. FreshReleaseGenerator (turtle/engines/taste/src/commonMain/kotlin/app/turtleplayer/taste/Generators.kt:206-228) defaults artists=40 (:209), builds wanted = topArtists(40) + boostedArtists + onboardingArtists, minus muted (:216-218), and calls releases.freshReleases(wanted, ...) (:222). YouTubeFreshReleases.freshReleases (turtle/bridge/src/commonMain/kotlin/app/turtleplayer/bridge/YouTubeFreshReleases.kt:109-126) computes stale = artists.take(MAX_ARTISTS).filter { not current } (:112), with MAX_ARTISTS = 15 (:269). Only those stale artists are passed to refresh/scan (:113, :146-200). Entries are read for the whole list (:114), but artists ranked 16 and below never get an entry unless they were in the top 15 at some earlier pass, so they contribute nothing. There is no rotation. The list order puts affinity artists first, so boosted and onboarding artists get dropped whenever 15 or more affinity artists exist. Followed artists: Shell's artist page has a Follow pill (turtle/ui/src/commonMain/kotlin/app/turtleplayer/ui/screens/ShellArtist.kt:514-515) that writes upstream bookmarkedAt (shared/src/commonMain/kotlin/com/metrolist/shared/state/ArtistSubscribeState.kt:45-49, :63). A grep of turtle/ for bookmarkedAt and ArtistSubscribe finds nothing outside that UI. The only "followed" read in bridge/ is for podcasts (TurtleSpoken.kt:155). No non-test code in bridge/ or ui/ writes boostedArtists or onboardingArtists.
- Proposal: Bridge: rotate the scan, refreshing the 15 stalest artists each pass from the full requested list, so all 40 are covered within a few cycles. The 12-hour cache and parallelism budget stay as they are. Add followed artists, read from upstream's DB through the existing database() accessor with no hook, to the 'wanted' set ahead of affinity artists. Engine: FreshReleaseGenerator takes followed artists as a seam and gives them a retrieval floor. Optionally add releases from CF-neighbour artists ('relevant'), marked with a distinct Reason. Users see new releases from every artist they follow and listen to.
- Risk: More network calls. Keep MAX_ARTISTS per pass and rotate instead of raising the cap. Followed artists with no listening may flood the shelf, so cap releases per followed artist (MAX_RELEASES_PER_ARTIST already 2).
- Verifier notes: The gap is real and it is a correctness bug: the generator asks for 40 artists and the source silently scans 15. It is not in the W1-W15 roadmap (spec lines 92-103). W4 onboarding will feed onboardingArtists, so W4 depends on fixing this ordering and cap, or onboarding picks will never reach Fresh for you when the listener has a history. It does not conflict with the rejected "new-music notifications" feature, because this is an in-app shelf and pushes nothing. It fits the privacy rule: follows are local DB state and YouTube scans already happen. The proposal to rotate the 15 stalest artists while keeping the 12h cache is sound and needs no hook, because the bridge can read upstream's DB directly. Followed artists with zero listening would get affinity 0, scoring 0.3 under the current formula. If they should rank above affinity artists, the generator needs the "retrieval floor" seam the claim describes. Small caveat on "never contribute": an artist who was in the top 15 earlier keeps its old cached entry, but that entry never refreshes.

### three-tier-slots (rec-surfaces, improvement, M, value medium, hooks 0, roadmap new)

**Only familiar vs discovery: no adjacent tier, and 'discovery' counts unheard songs by favourite artists**

- Paper: 2.5: three categories (familiarity, adjacent discovery, exploration) in an adaptive ratio. 2.3: deliberate exploration beyond the obvious neighbourhood.
- Evidence: Confirmed in turtle/engines/taste/src/commonMain/kotlin/app/turtleplayer/taste/: SlotKind has only FAMILIAR("f") and DISCOVERY("d") (Candidates.kt:27-32). ScoredCandidate.slot is FAMILIAR only when Feature.HEARD_BEFORE > 0, else DISCOVERY (Ranker.kt:107; HEARD_BEFORE is set from the track's own play count, Features.kt:148, and ARTIST_HEARD_BEFORE is a separate ranker feature, Features.kt:149, weight 0.2 at Ranker.kt:59, which actively favours known artists inside the discovery slot). planSlots emits a two-way pattern by error diffusion (Exploration.kt:112-123), sampleShare draws one Beta share (Exploration.kt:104-105), and QueueAssembler swaps to the other kind on shortage (Queue.kt:145). The single exploration posterior is updated for any DISCOVERY-tagged play (TasteEngine.kt:201-202), so an unheard track by the top artist and a track by a never-heard artist feed the same posterior. Partial mitigation the claim omits: Weekly Discovery's radio fallback orders never-heard artists first (TasteEngine.kt:974-976), but its main vector path (TasteEngine.kt:958-971) only filters never-heard tracks, with no artist-novelty split, and Weekly Discovery already uses familiarShare 0.0 (TasteEngine.kt:971). Shelves call compose -> planSlots with a fixed familiarShare (TasteEngine.kt:786-798). SurfaceTag.parse returns null for an unknown slot tag (Candidates.kt:92), and KeptShelves decodes slots with entries.first (KeptShelves.kt:140), which would throw on an unknown tag in an older build, so the risk note understates the persistence concern for kept shelves.
- Proposal: Engine: add SlotKind.ADJACENT, meaning an unheard track by a heard artist or inside a taste cluster above a similarity threshold. DISCOVERY becomes exploration: a new artist outside the nearest cluster. planSlots takes a three-way split (familiar, adjacent, explore), and exploration Thompson-samples the explore share separately from the adjacent share. Successes on explore slots (finish, save, later replay) feed their own posterior. Per surface: Daily Mix about 70/25/5, Weekly Discovery 0/40/60, both shifted by the dial.
- Risk: The new slot tag is persisted in surfaceDetail. SurfaceTag.parse returns null for an unknown slot (Candidates.kt:92), so older builds reading new data degrade safely and old data still parses. The existing exploration posterior must be migrated or treated as the adjacent posterior. Replay gate applies.
- Verifier notes: Gap is real and lives entirely in turtle/engines/taste (0 hook lines). Not covered by W4-W15 in docs/specs/2026-11-22-personal-home-design.md:95-104 (W10 is a learned ranker and vectors, not a slot taxonomy); no doc mentions an adjacent tier. No rejected-feature conflict. Caveats: (1) KeptShelves.kt:140 uses SlotKind.entries.first, so a downgrade reading kept shelves with a new "a" tag would crash rather than degrade; the new tag must be handled there, not only in SurfaceTag.parse. (2) The proposed per-surface ratios (70/25/5, 0/40/60) are invented numbers, not from code or spec; Weekly Discovery is already 0% familiar. (3) A cheaper first step is splitting DISCOVERY by ARTIST_HEARD_BEFORE (known vs new artist) for the posterior and Weekly Discovery ordering before adding cluster-distance thresholds. W12 ('a real offline eval', Wave 3) only partly overlaps: an on-device log of failed queries could feed the golden set or offline replay in turtle/AGENTS.md:31, so the 'copy failed queries' part fits naturally inside W12. W14 (stats) is for the listener, not for diagnostics. Nothing in the proposal is a rejected feature, and it stays inside the privacy rule (turtle/AGENTS.md:40) if it is local only, follows W3's pause and clear-history rules, and shows only on an opt-in page. It needs no new hook because ShellSearch is Turtle-owned. Two caveats. Upstream Metrolist already stores search query history, so the text of past queries is not new on the device; what is new is outcome data (result count, first-play rank and time, reformulation). Also, for a single-user client this is mainly a developer-tuning tool, so its value to listeners is indirect. Build it alongside or after W5, or fold it into W12, rather than as a standalone workstream.

### recommendation-health (measurement, new-feature, M, value medium, hooks 0, roadmap new (feeds W10; listener-facing parts are W14))

**Attribution data exists, but no per-surface quality numbers are computed**

- Paper: Section 13 table: Recommendation quality (skip rate, saves, diversity, long-term return); Personalization (profile correction rate); Trust (unwanted-recommendation reports); Listening (playback failures). Also 'Keep user control visible'.
- Evidence: Attribution exists and is recorded, but nothing reads it back grouped by place. PlayPlace is set at play time in ShellHome.kt:262,269,477,483,491,588, ShellSearch.kt:630 and SmartShuffleBridge.kt:79, and written into surfaceDetail by SurfaceTag.format (Candidates.kt:80). The only reader of the tag is TasteProfile.kt:429-430, and it keeps SkipStats (plays, quickSkips only: TasteProfile.kt:79-82) per CandidateSource. It does not group by PlayPlace or row, has no finish rate, saves, not-interested counts or errors, and covers no time window. A grep for `.place` in engines, bridge and ui finds no other consumer of origin.place. ReplayEvaluator (taste/eval/ReplayEvaluator.kt:38-80) computes recall, NDCG, novelty and coverage offline on held-out history for CI. It does not measure live per-surface outcomes. W1 row thresholds are tuned only from TurtleLog lines (TurtleHomeRows.kt:150-155; w1 plan "Initial thresholds ... The bridge logs every row's score for that tuning. The offline replay doesn't exercise row selection").
- Proposal: Taste engine: a pure function over PlayEventStore.since() and feedbackSince() returning per PlayPlace and row, over 7 and 30 days: plays, quick-skip rate, finish rate, saves per 100 plays, not-interested per 100 impressions-played, new-artist plays and the share retained (same rule as retained-discovery-metric), and error-ended plays. The bridge exposes it. A 'Recommendation health' page under Turtle settings (developer/diagnostics, off the main path) shows it, on device only. Later, W10's ranker training and W14's listener-facing stats can read the same API.
- Risk: Impressions (rows shown, not played) are not logged, so rates per impression need a separate shown-event, or the metrics must stay per play. Strings must be localized in Turtle's resources. Must not become telemetry.
- Verifier notes: The gap is real. The spec's program table (personal-home-design.md:96-104) has no workstream for on-device per-surface metrics. W9 (spec :226-250) says the row key is recorded "so Wave 4 can learn which YouTube rows the listener actually plays", W10 is the learned ranker, W12 is "a real offline eval", and W14 is listener-facing stats and Wrapped. This proposal would feed W10 and W12, but none of them plans it, so it counts as new. It does not touch any rejected feature, and it keeps to the privacy rule if it stays on device with no export. The UI surface should be framed as a diagnostics/developer page, because a listener-facing version overlaps W14. The risk is accurate: impressions are not logged, so metrics per impression would need a new shown-event, which adds data-model work. Starting with per-play metrics avoids that. User value is mostly for the developer, who tunes thresholds and judges W1/W7 rows, and listeners do not see it directly. Even so, it removes the only current tuning method, reading log lines, so medium/low value with 0 hook lines is fair.

### real-history-replay (measurement, improvement, M, value medium, hooks 0, roadmap W12)

**The replay runs only on 30 synthetic users built from the same genre assumptions as the engine**

- Paper: Section 13, 'Measure long-term satisfaction' and 'Recommendation quality': offline metrics must reflect real listening, not a model of it.
- Evidence: The evidence is accurate. In turtle/engines/taste/src/commonTest/kotlin/app/turtleplayer/taste/OfflineReplayTest.kt, lines 21-22 build `SyntheticWorld()` and 30 synthetic users (`(0 until 30).map(world::user)`). The evaluator, the popularity baseline and the random baseline all use `world.tracks`. In SyntheticWorld.kt, `history()` (about lines 99-140) generates plays from the user's liked genres, favourite artists and a heavy-rotation set: about 80% in-taste and mostly COMPLETED, 20% popular out-of-taste and 85% SKIPPED at 8s. Every event is tagged Surface.LIBRARY / StartReason.AUTOPLAY. ReplayEvaluator (taste/src/commonMain/.../eval/ReplayEvaluator.kt) is used only by OfflineReplayTest, and SyntheticWorld is used only by the taste tests. No replay runs on real or fixture histories anywhere in turtle/. The only events test is engines/events/src/commonTest/.../EventsTest.kt, and no checked-in JSON fixture resources were found. The importers exist: engines/events/src/commonMain/kotlin/app/turtleplayer/events/imports/ListenBrainzHistoryImporter.kt, SpotifyHistoryImporter.kt and PlayerHistoryImporter.kt. The spec, turtle/docs/specs/2026-11-22-personal-home-design.md line 103, lists "W12 a real offline eval" in Wave 3 with 0 hook lines.
- Proposal: W12 as planned: add reduced fixture histories from a public, permissively licensed dataset (for example ListenBrainz dumps, after checking their licence per AGENTS.md) and parse them through ListenBrainzHistoryImporter. Run the same ReplayEvaluator targets (including RETAINED) with checked-in baselines. Never commit the owner's own history; a local-only Gradle task can replay their exported history for private tuning.
- Risk: Dataset licence and size (keep fixtures small for CI time). Real histories lack Turtle's surface tags and skip reasons, so some metrics only apply to synthetic or on-device data.
- Verifier notes: The gap is real, but it is already planned as W12 and should not be counted as a new idea. Detailed design is deferred: the spec says Wave 2 onward gets its own design pass, and no W12 plan exists in turtle/docs/plans. The proposal fits AGENTS.md. Line 33 says "Parsers ... get fixture tests from real, reduced files", and lines 41-42 say to check every dataset licence. The ListenBrainz listen dumps are generally CC0, so they should be compatible, but the W12 design must confirm that.

Two caveats:
1. ListenBrainz listen records carry no genre. AGENTS.md forbids MusicBrainz genre/tag data because of its non-commercial licence, so a fixture cannot be enriched with MusicBrainz tags to give the engine's genre vectors something to work on. Track metadata for the fixture world has to come from a permissive source, or the evaluation runs on artist/co-listening signals only.
2. Real dumps lack skips and msPlayed: ListenBrainz logs only submitted listens. So the NEW_ONLY and ALL_FINISHED targets can only be approximated, and signals from skip outcomes cannot be measured.

The private, local-only replay of the owner's own export fits the privacy rule as long as it never leaves the device or the repo. Size is M, needs no hook lines, and lives entirely in turtle/engines/taste tests.

- **more-like-this**: Refuted. The user-facing ability that paper §4.3 and §11.5 ask for, a simple way to say "more like this", already exists. "Start radio" and the "More like X" shelves also cover asking for more of a sound.

What remains is narrower. The engine has boost fields with no caller, so there is no artist-level or cluster-level boost separate from liking a song. - **version-chooser**: Not in the spec or the plans: a grep of turtle/docs finds nothing on versions, remasters or alternates. The engine half of the proposal (making remaster a tag) goes against tested identity rules that taste dedupe and the golden set depend on, so it conflicts. The only new part left is a chip row of sibling versions under the top card. That is a small UI nicety, because searching with a version word already does this and titles already carry the version text. Not worth flagging as a gap. - **phone-touch-targets**: Refuted as a functional bug. Compose's automatic touch-target expansion on touch input already gives these phone controls a 48dp hit area, even though they draw at 20-36dp. What actually differs is the layout and semantics bounds: an accessibility scanner may flag them, and TalkBack's focus outline would be smaller. That is a lint-level or cosmetic issue, not hard-to-hit controls. Adding `minimumInteractiveComponentSize()` would mostly change layout height, as the claim's own risk note admits, without improving hit-testing. Caveat: I did not open the Compose UI sources in the Gradle cache. The expansion behavior comes from knowledge of Compose UI's NodeCoordinator hit testing (minimumTouchTargetSize). Someone should check it on a device with "Show layout bounds" or by tapping just outside a chip before deciding it is not worth doing. Not planned in W4-W15, and it does not conflict with rejected features.
- **song-details-sheet**: Refuted as stated. Codec, bitrate, loudness, size and play totals are still reachable under Shell: long-press or open the menu on any song row in Shell's Home, Artist, Collection or Library pages. That opens upstream's item menu, which has a Details action on Android, mobile and desktop. The playing song gets live stream data there too. What remains is a small discoverability gap: Shell's Now Playing More sheet (phone and desktop) has no shortcut, and the upstream-player handoff its KDoc describes is dead code. That is a one-row convenience fix, not lost functionality. If it is done, wire it to upstream's existing SongDetailsContent with the live playbackResource. The stale KDoc at ShellPlayer.kt:419-422 and HOOKS.md #26 should also be corrected. The paper's credits point stays unmet either way: SongWatchInformation has no structured writer or producer credits. That is a separate, larger gap. None of this is in the W1-W15 roadmap or among the rejected features.
- **locale-separators**: I am refuting this because the change would not alter anything users see. Turtle's Shell UI has no translated string catalogs, only the base values/strings.xml. A new list-separator string or a `metaJoin()` helper would therefore render exactly the same characters in Japanese, Arabic and every other locale. The fix only matters once Turtle strings are translated through Weblate, and that is not set up for turtle/ui. Until then it is a consistency cleanup.

Two further points. Joining artists with ", " is the same convention upstream Metrolist uses everywhere, so there is no Turtle-specific bug. The middle dot and bullet are typographic separators rather than translatable words. The project rule against hardcoded user-facing text is aimed at words, not punctuation.

There is one minor real inconsistency: ShellCollection mixes " • " with " · " elsewhere. That is purely cosmetic.

Nothing in turtle/docs plans this, and it does not conflict with any rejected feature. It could be reconsidered as a small i18n-hygiene PR if Turtle strings are ever opened to translation. If so, the helper should live in ShellComponents and reuse `shell_meta_pair`.
- **recap-share-card**: Refuted as a new gap. Tap-only image sharing of aggregate listening stats already ships through upstream's Statistics screen, which Shell links to on desktop and phone. The remaining difference is styling: a Shell-palette card with Turtle branding and Turtle-specific fields such as "new finds". That belongs in W14 (stats and Wrapped, Wave 4), whose spec says it gets its own design pass, so it should not be proposed separately now. The proposal fits privacy and rejected-feature rules: it is opt-in, aggregate only and user-initiated. When W14 is designed, the iOS bridge gap and the artwork-before-capture risk the claim names are worth carrying into that design. Another option for W14 is to send users to upstream's existing share path instead of writing a new expect/actual shareImage.

### search

- Typo-tolerant term matching: exact > prefix > fuzzy (1-2 typos by length) > fuzzy-prefix > infix, with adjacent-swap handling for 3-letter tokens and a bit-parallel edit-distance matcher (turtle/engines/search/.../TermMatching.kt:7-116, BitParallelMatcher.kt).
- Text normalization folds case and accents, transliterates Cyrillic and kana (Hepburn) to Latin, widens full-width chars, expands ft/feat/pt/vol (turtle/engines/core/.../TextNormalizer.kt:4-24, 138-181). Devanagari and other abugidas are kept, with their essential marks preserved, but not romanized (TextNormalizer.kt:76-77).
- Intent recognition (rule-based, swappable IntentClassifier): ARTIST, SONG, ALBUM, SONG_BY_ARTIST ('x by y', 'a - b', 'coldplay yellow' in either order), LYRICS (cue words or long function-word-heavy queries), MOOD (mood/activity/genre vocabulary), and cue words 'album/ep/lp', 'lyrics', 'song/track' (QueryParser.kt:7-22, 307-439). Known names come from library lexicons plus optional extra artists (SearchEngine.kt:88-94).
- Plain-word filters: version words (live, acoustic, remix, cover, instrumental, karaoke, slowed/reverb, sped up/nightcore, demo, orchestral) and years/decades ('2014', '90s', '1980s'). A query that is exactly a known title or artist ('Live Forever', the band 'Live') skips filter extraction (QueryParser.kt:169-171, 202-266; core VersionTag at TitleCanonicalizer.kt:4-15).
- Entity and version understanding: TitleCanonicalizer strips upload noise and pulls out version tags and featured artists. ResultMerger dedupes uploads by union-find over key, ISRC, YouTube id and a canonical artist|title|versions identity, then prefers the official upload, then the user's copy, then popularity (ResultMerger.kt:188-225, 500-504). Channel suffixes '- Topic' and 'VEVO' are cleaned (ResultMerger.kt:485-494).
- Ranking blends relevance 0.62, intent 0.12, affinity 0.14, popularity 0.05 with version, library/history and year adjustments. Requested versions get a boost, unrequested live/remix and covers/karaoke get penalties (ResultMerger.kt:11-46, 288-302). The intent-matched top result may trail the best item only by topIntentSlack 0.85, and an online artist named exactly like the query wins when song confidence is low (ResultMerger.kt:121-155). An exact match keeps its lead over a merely-favored partial match by these weights, and the golden query set enforces top-1 >= 0.96 and top-3 >= 0.98 with affinity on (commonTest/.../golden/GoldenQuerySetTest.kt:33,66,121-122; SearchEngineTest.kt:119-130).
- Cross-script fallback: an online result written in a different script from the query keeps its full provider-rank evidence (ResultMerger.kt:439-456).
- Parallel staged retrieval: local first within 30ms, then semantic (120ms) and online (600ms) deadlines, emitting progressively (SearchEngine.kt:52-154). SemanticRetriever is an interface with only a None implementation (Providers.kt:80-92).
- LyricsIndex is built: fragments of 3+ words match two-line windows with typo tolerance, LRC timestamps are stripped, and lyric-led tracks are grouped as SearchResults.lyrics (LyricsIndex.kt:21-63; ResultMerger.kt:95-114; SearchEngine.kt:171-179).
- Personal suggester is built but unwired: SearchSuggester ranks recent searches (typo-tolerant, in order), then library/history tracks, artists and albums (played above saved), then online completions. An empty box shows recent searches plus recently played (Suggestions.kt:92-198). InMemorySearchHistory with a persistence seam is also built (Suggestions.kt:39-90). No class outside engines/ constructs SearchSuggester or InMemorySearchHistory (grep across turtle/bridge, turtle/ui, shared).
- Interim affinity: HistoryAffinityProvider uses saturating play counts over 180 days and ignores quick skips (Providers.kt:94-137). It is used by TurtleSearch (TurtleSearch.kt:40). W5 plans taste-based affinity.
- Bridge: TurtleSearch.rerank re-ranks upstream's already-fetched summary page with the library through hook #20 (YouTubeRepository.kt:1572; TurtleRuntime.kt:127,195-203). It rebuilds Top / Songs / Artists / Albums and passes videos, playlists and podcasts through unchanged. It fails open to upstream's page after 800ms or when nothing ranks (TurtleSearch.kt:42-105). Library songs are pinned in SongCache, so local hits are playable (SongCache.kt:7-19; LibrarySync.kt:95-96).
- Library-tab search uses the same index through hook #4, libraryContentSearchOverride (turtle/HOOKS.md:29).
- A Koin singleton SearchEngine with YouTubeOnlineSearch (which implements suggestions via getSearchSuggestions) is declared but no code consumes it (TurtleModule.kt:111; YouTubeSeams.kt:25-44).
- UI (ShellSearch.kt) with an empty query shows upstream's recent searches (238-240), four static 'vibe' chips and eight static genre tiles. Each runs a plain text search (strings.xml:32-43; ShellSearch.kt:251-253). While typing it shows upstream's YouTube suggestions and recommended items only (203-204, 258-266). After submit it shows chips for Top/Songs/Artists/Albums/Playlists (+Podcasts/Episodes) (152-163), the top result beside songs on wide screens, and card rows. The 'no results' message offers the same static vibe chips (288-291). Skeleton, retry and a liked badge exist. Song plays are attributed to PlayPlace.SEARCH with no detail (630).

### catalog-library

- Title canonicalization: TitleCanonicalizer.canonicalize turns upload titles into a base title, VersionTag set (LIVE, ACOUSTIC, REMIX, COVER, INSTRUMENTAL, KARAOKE, SLOWED, SPED_UP, DEMO, ORCHESTRAL), featured artists and an `official` flag (turtle/engines/core/src/commonMain/kotlin/app/turtleplayer/core/TitleCanonicalizer.kt:4-24, 67-134). It penalizes covers, karaoke and unrequested versions, and boosts a requested version (ResultMerger.kt:288-296). ### social-recaps

- Turtle keeps its own on-device play log in a separate SQLite file (`turtle.db`, TurtleDatabase.android.kt:7-8). Its `play_event` table (SqlitePlayEventStore.kt:105-140) stores, for every play: track, artists, album, release date, start time, ms played, duration, start and end reason, surface and surface detail, seeks, replayed, liked, added-to-playlist, less-like-this, hour, weekday, device, network and source. Indexes exist on start time, track, artist and source (:52-55). Nothing prunes old plays: the only delete is by import source (:292-298). That is enough to build a recap with no new data collection.
- PlayEvent already gives a recap what it needs. `isQuickSkip` (PlayEvent.kt:95) is a skip in the first 30s, `isFinished` (:98-99) a play heard to the end, `isListen` (:102) a counted listen, and `completion` (:92) the share of the song heard. PlayContext (:41-56) has hour, weekday and an hour bucket for a 'when you listen' view. EventSource (:35) tells local plays apart from Spotify, Last.fm, ListenBrainz and Metrolist imports.
- Things done outside a play are logged too: TrackFeedbackKind ADDED_TO_PLAYLIST, NOT_INTERESTED and UNDO_NOT_INTERESTED (TrackFeedback.kt:6), stored in `track_feedback` (SqlitePlayEventStore.kt:80-101) and read back with `feedbackSince` (PlayEventStore.kt:40).
- The store API offers only `since(sinceMs, limit)`, `forTrack`, `forArtist` and `count` (PlayEventStore.kt:24-34). It has no aggregate queries. `since` builds a full PlayEvent per row (SqlitePlayEventStore.kt:271-276, 422-475).
- The taste engine already computes the stats a recap needs. TrackStats has plays, finishes, quickSkips, likes, replays, firstPlayedMs, lastPlayedMs, recentFinishes and `foundMs`, the moment the listener 'found' a song (TasteProfile.kt:85-111). ArtistStats has affinity, plays, finishes and a context mix (:114-126). A 'new find' signal (:30, :470-478) and a found-recently pick (TasteEngine.kt:916-917) already exist. Taste clusters come from SphericalKMeans with up to 8 clusters (Clustering.kt:10-14). ShelfKind.ON_REPEAT is 'their most-finished tracks of the last 30 days' (Surfaces.kt:28-29).
- The log keeps only music the listener chose to have learned. Spoken word is not recorded (PlayerObserver.kt:51-52, :177). Paused history stores nothing (ListeningSessionTracker.kt:88-89, :111). A recap built on `play_event` therefore inherits the privacy and podcast rules automatically.
- History from before Turtle is backfilled once from upstream's event table as METROLIST_IMPORT, podcasts excluded (MetrolistHistoryImport.kt:27-45). An imported row with no known play time is stored as `msPlayed = LISTEN_MS` (30s) with end reason UNKNOWN (PlayerHistoryImporter.kt:44-47). Spotify and ListenBrainz importers are registered in Koin (TurtleModule.kt:103-104), but no Turtle UI calls them.
- Upstream (Metrolist) has a full Statistics screen. It offers WEEK, MONTH, THREE_MONTHS, SIX_MONTHS, YEAR and ALL periods, with calendar mode, totals, top tracks, albums and artists, plus daily and hourly heatmaps (StatisticsScreen.kt:169-208). It also has an image share card (StatisticsShareDialog.kt:64), which Android exports through `shareImage` (StatsScreen.kt:67, ImageSharing.kt:14-40). It reads upstream's `event` table (HistoryStats.kt:71-118, 192+), not Turtle's richer log. Turtle surfaces it only as a desktop nav destination (ShellDesktop.kt:224, :234). On Android, upstream opens it from the account popup (MetrolistApp.kt:1005); I did not verify whether Shell's phone UI still exposes that popup.
- Upstream's share mechanisms: song, playlist and album links (ShareUrls.kt:6-23, to music.youtube.com). Android text share uses an ACTION_SEND chooser (AndroidPlayerPlatformServices.kt:76-84; PlaylistScreen.kt:889-896; AlbumScreen.kt:462; BrowseScreen.kt:182-210). Android image share goes through FileProvider `${applicationId}.fileprovider` with `cache-path images/` (AndroidManifest.xml:91 and its paths xml). Desktop uses a ShareSheet (AppState.kt:143-153) and copies links from the context menu (ItemContextMenu.kt:798). iOS has `IosNativeFiles.shareText` and `shareImage` (IosNativeFiles.kt:177, :205).
- Phone Shell's player shares the current song through upstream (ShellPlayer.kt:795, `share = { vm.shareSong(it) }` -> PlayerViewModel.kt:1261-1262). Desktop Shell's player passes `share = null` (ShellDesktop.kt:484).
- Turtle turns Listen Together off (TurtleUi.kt:39: `hideListenTogether = true`, scrapped by the product owner on 20 Nov 2026). Turtle has no recap, Wrapped, compatibility or Blend code: grepping turtle/ for recap and wrapped matches only unrelated comments. ### measurement

- Offline replay evaluator: hides each user's last N days, recommends from the rest and computes recall@K, binary NDCG@K, novelty (mean -log2 popularity) and catalog coverage. It has two holdout targets, ALL_FINISHED and NEW_ONLY (never heard in training) (turtle/engines/taste/src/commonMain/kotlin/app/turtleplayer/taste/eval/ReplayEvaluator.kt:31-55, 62-120). It accepts only PlayEvents (line 68); TrackFeedback saves are not an input.
- OfflineReplayTest runs the evaluator on 30 synthetic users (SyntheticWorld). It requires the engine to beat popularity and random by 1.5x on recall and NDCG, gates recall@50 and NDCG@10 at 98% of hand-set golden constants (0.587/0.868 all-finished, 0.960/0.641 new-only), and checks determinism (turtle/engines/taste/src/commonTest/kotlin/app/turtleplayer/taste/OfflineReplayTest.kt:42-91). Novelty and coverage are printed but never asserted (lines 47-49, 81-84).
- The replay adapter scores only TasteEngine.recommendations(), which ranks through the autoplay collector (TasteEngine.kt:582-586; ReplayEvaluator.kt:18-29). Shelves and Home row selection are not replayed; the W1 plan says so: 'The offline replay doesn't exercise row selection' (turtle/docs/plans/2026-11-22-w1-personal-home.md:76).
- Synthetic history: 80% in-taste plays, 20% popular out-of-taste plays that are mostly quick-skipped. Each user has 30 'discoverLate' tracks first played in the last 30 days, at 25% of plays (turtle/engines/taste/src/commonTest/kotlin/app/turtleplayer/taste/SyntheticWorld.kt:95-140).
- Search golden set: 96 queries in 12 categories (EXACT, TYPO, PARTIAL, SONG_BY_ARTIST, ACCENTS, SCRIPTS, VERSION, LYRICS, PERSONAL, ALBUM, MOOD, YEAR), described as growing 'toward the plan's 500 real queries' (turtle/engines/search/src/commonTest/kotlin/app/turtleplayer/search/golden/GoldenQueries.kt:14, 19-20). They run through the full engine with fake online results and history affinity, with absolute floors of top-1 >= 0.96 and top-3 >= 0.98. Per-category rates are printed only (GoldenQuerySetTest.kt:85-123).
- Search latency behavior is unit-tested: local results come first, and the online and semantic deadlines are enforced (turtle/engines/search/src/commonTest/kotlin/app/turtleplayer/search/SearchEngineTest.kt:55-75, 179-188).
- CI runs every engine test, including both golden gates, on every pull_request and on pushes to main, and uploads the reports (.github/workflows/turtle-engines.yml:3-6, 22-38). There is no CODEOWNERS file. Whether the job is a required status check is a branch-protection setting the repo cannot show, so enforcement is unverified.
- On-device play log with typed signal definitions: quick skip under 30 s, finished (COMPLETED, or 80% or more for imports), listen (PlayEvent.kt:94-107). EndReason.ERROR exists (PlayEvent.kt:23-33).
- Play attribution (W9): PlayPlace covers ENGINE, INFINITY, SMART_SHUFFLE, RADIO, SEARCH, HOME_TURTLE, HOME_GRID, HOME_RECENT and HOME_YOUTUBE (Candidates.kt:35-55), encoded by SurfaceTag (Candidates.kt:67-102) and written per play by PlayerObserver (turtle/bridge/src/commonMain/kotlin/app/turtleplayer/bridge/PlayerObserver.kt:213-236). A search tap is tagged 'search/-/-' with no query or result position (turtle/ui/src/commonMain/kotlin/app/turtleplayer/ui/screens/ShellSearch.kt:625-630; PlayerObserverTest.kt:150-155).
- Non-play feedback is stored with timestamps: ADDED_TO_PLAYLIST, NOT_INTERESTED and UNDO_NOT_INTERESTED (turtle/engines/events/src/commonMain/kotlin/app/turtleplayer/events/TrackFeedback.kt:6-16; PlayEventStore.feedbackSince at PlayEventStore.kt:40).
- Skip rates exist only as ranking features, per artist, cluster and generator source, fed from SurfaceTag (Features.kt:47-49, 140-169; Ranker.kt:69-71; TasteProfile.kt:429-431). They are never reported as a metric.
- Familiarity/discovery balance (paper 2.5): Thompson sampling over one global Beta posterior for the discovery share, clamped by the listener's dial (Exploration.kt:57-124; UserControls.kt:10-30). The dial is in the player and settings UI (ShellPlayer.kt:566-592; ShellSettingsTurtle.kt:375), and the state persists (TasteState.kt:19, 71-72).
- First-play 'new find' detection in the profile: a first play held at least ENGAGED_MS and not skipped before halfway (TasteProfile.kt:463-470).
- User control and trust: a hidden songs, artists and shelves list with undo (UserControls.kt:92-129; ShellHidden.kt), and upstream's local Block list read live (bridge/NotInterested.kt, UpstreamBlocks.kt).
- Device-side diagnostics are logs only: Home row scores are written to the on-device DriveLog for threshold tuning (TurtleHomeRows.kt:155; DriveLog.kt:13-28, kept on device, capped and rotated). Search shows a no-results message (ShellSearch.kt:289), but nothing counts it.
