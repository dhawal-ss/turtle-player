# Turtle status and handoff

**23 November 2026 · `main`**

This is where Turtle's product work stands, so any machine or session can pick it up from the repository alone. Read it before starting new work, then read the documents it links.

## How we work

- **One branch.** All work happens on `main`. Don't create feature branches or extra worktrees; side branches have already hidden finished work (the credits heart) and caused a fix to be redone twice. If a session needs isolation, merge its result into `main` at once and delete the branch. See `turtle/AGENTS.md`.
- **Commit and push only when the owner asks.**
- **Run one Gradle build at a time.** Parallel builds hit Kotlin incremental-cache errors and out-of-memory failures.
- **Never run a ktlint `*Format` task.** The `turtle-ui` and bridge modules are not ktlint-clean, so it rewrites many unrelated files. Run `*Check` and fix only the lines you changed.
- **Bridge desktop tests** point every XDG home into `turtle/bridge/build/test-xdg`. They never touch the developer's real Turtle database or Metrolist settings, so the whole bridge suite is safe to run, `TurtleRuntimeTest` included.
- **Desktop UI screenshot tests.** `./gradlew :turtle-ui:desktopTest` renders the real `ShellDesktopLayout` headless (harness in `turtle/ui/src/desktopTest/.../shot/`) and writes PNGs to `turtle/ui/build/screenshots/`. They cover the narrow-window Queue overlay, Explore Back keeping its scroll, mix details and search ordering. Upstream pages are stand-ins, so check real pages in the app.
- **Don't build Turtle modules while `:desktopApp:run` is running.** Rebuilding a module jar under the running app (for example `:turtle-ui:desktopTest` or the Android compile after a string change) makes Compose fail to load strings from it (`ZipException: invalid LOC header`) the next time a screen needs one. Stop the app first, then restart it.
- **Desktop sign-in in a dev run** needs the .NET 10 SDK and the login helper built into `desktopApp/src/desktopMain/resources/windows/` (see the Windows job in `turtle-release.yml`).
- **A fresh checkout or worktree** needs `git submodule update --init` (`metroproto`, `libopus`) before an Android build. It also needs `ANDROID_HOME` set when there is no `local.properties`.

- **Upstream's Spotify playlist importer.** Turtle reaches it: Shell Settings → Library → Backup & restore opens upstream's page. There, `SpotifyImportManager` (`shared/src/jvmSharedMain/.../spotifyimport/SpotifyImportManager.kt`) signs in with the `sp_dc` browser cookie and loads playlists over the network. On Android, opening the page restores a saved Spotify session, which makes network calls. On desktop, a `collection/tracks` link opens the same flow. This conflicts with "imports read only files the user downloads themselves" (`turtle/AGENTS.md`). It imports playlists, not history, and nothing in Turtle calls it. Left unchanged and not advertised until the owner chooses:
  - **(a)** Drop Backup & restore from Shell's settings list. This is Turtle-only, but it also hides upstream backup and restore.
  - **(b)** Hide the Spotify provider and account entries with approved hooks. That is about 2 to 4 upstream lines on the two platforms.
  - Don't link history import or Spotify migration from setup or Library before this is settled.
- **Desktop welcome "Start listening".** It bypasses artist picks; routing it needs one more hook line in `DesktopOnboarding.kt`.

## Next in the plan

- **History import UI (roadmap step 5a follow-up).** The engine side is done but not committed. Imports are stage, then preview, then explicit commit (`SpotifyHistoryImporter.stage`, `ListenBrainzHistoryImporter.stage`, `PlayEventStore.commit`). The preview counts accepted, duplicate, unresolved, rejected, non-music, private-session and excluded rows. Input is bounded by `ImportLimits`. The store replaces a source atomically (`replaceSource`, one SQLite transaction). `TurtleRuntime.commitHistoryImport` and `removeImportedHistory` write and then rebuild under `NonCancellable`. A wrong, empty, broken or canceled import leaves stored history unchanged. Still missing:
  - **Platform file reading.** SAF `OpenDocument` plus `ZipInputStream` on Android, and a file dialog on desktop, in bridge `androidMain` and `desktopMain`. Both must count uncompressed characters per entry against `ImportLimits.maxFileChars`.
  - **A preview and confirm screen.** It must also confirm before `shrinksHistory` replaces older history.
  - **On-device checks.** Commit time for a large Extended export on Android, and whether playback recording continues during the commit (it waits on the store lock). Killing the app mid-commit must leave the prior import intact.
- **Measurement gates (roadmap step 5c), done but not committed.** No learned ranker is built or trained.
  - **Replay.** It keeps the historical capped recall (`recall@50`, hits divided by min(holdout, 50)) under its old label, and appends standard recall (`standardRecall@50`, hits divided by the holdout size). Synthetic baselines: all-finished capped 0.587 and standard 0.487; new-only 0.960 for both. Both are gated at 2%.
  - **Listener outcomes** (`taste/eval/ListenerOutcomes.kt`, developer-only, `Clock`-injected):
    - `FirstFiveSkips` gives first-five early skips per surface over 28 days. An unknown end under 30 s is counted as unknown, outside the rate. Runs that playback ran on into, from an untagged play or at the start of a session resumed after a long pause, are counted as joined and are never eligible; this covers desktop's untagged first radio page.
    - `DiscoveryReturn` gives the 7-day discovery save-or-replay rate. Songs are matched by `SongKeys` identity, and new-artist rows are listed apart.
    - Both read from the `measure_since_v1` pref (`PREF_MEASURE_SINCE`). `SaveWatcher` writes it once, on the first launch of this build.
  - **New `SAVED` feedback kind.** `SaveWatcher` records in-app likes (`SongLikeState.newLikes`) and library adds (a diff of `LibrarySync.saved` with the playlist-add settle and burst rules) while history is recording (a library add first seen while paused is never recorded). It is used for measurement only: the taste engine ignores `SAVED`.
  - **Probe.** The origin probe now also prints both reports and their unknown or untagged shares.
  - **Learning follow-up.** In-app likes still never reach `TasteEngine.setSavedTracks`, because `SongLikeState` does not write `Song.liked`. Feeding them needs unlikes and like times, not only the new-like stream. `SavedTrack.atMs` for library adds is also shifted by the UTC offset.
- **Small wins from the Spotify comparison.**
  - Make Browse tiles open Infinity genres (Search tiles open YouTube's category pages once Home has loaded).
  - Add a Stations row, a Charts entry and a lyrics preview.

## Known issues

- **Replay baseline.** Matched Home keeps no YouTube rows on the test phone, because history recorded before `5a3f0c5e` and `91413ef4` holds false skips: 80 of 128 quick skips. Read the drive log's `player observer:` lines after real use to see which path still produces unknown starts. Stored history was left unchanged.
- **Podcast-typed songs.** Songs YouTube types `PODCAST_EPISODE` count as spoken word (24% of India's weekly chart), so they never teach taste or reach Home rows.
- **Radio fallbacks.** Upstream's content filters (explicit, videos, blocked) run on every radio page at fetch time on both platforms. `TurtleRuntime.rankRadio` now applies Turtle's exclusions (Not interested songs and their other uploads, muted artists, duplicate uploads, the seed's other upload) on every way out, ranked or not, and pages past a page with nothing left (at most 3 pages, about 2 s). Muted taste clusters still apply only when ranking finishes. Artist radio and desktop Related songs get no Turtle exclusions. Android's end-of-queue path keeps the station's token on an empty page (behavior patch #62), so it no longer refetches the same page.
- **Infinity.** The genre search queries are fixed English phrases (`InfinityGenres`).
- **Upstream bugs.** `YouTubeRepository` throws "Playlist continuation cycle" for some playlists past 100 songs. Report it to Metrolist.
- **Car playback.** Playback can stop when the phone locks in the owner's car over Bluetooth and USB. A driveway test worked; the cause is unconfirmed. Turtle writes a drive log to `files/turtle-drive.log` in the app's data. After a car test, read `adb shell dumpsys audio` at once.
- **Smaller issues.**
  - The first song of a mix started from a Home card is recorded with no detail.
  - Theme palette cards expose no selected state to screen readers.
  - Library rows lack the explicit tag that collection rows show.

- **Reading data.**
  - Use `adb exec-out run-as com.metrolist.music.debug.t2 …` to read the drive log or copy `databases/turtle.db`.
  - Keep copies off the repository.
  - Report aggregates only: listening history stays private.
- **Origin report and listener outcomes.** Run the probe on each platform's database copy separately; that is the platform split. Use `./gradlew :turtle-bridge:desktopTest --tests '*LocalOriginReportProbe*' -PturtleOriginReportDb=<copy>`.
- **Wireless adb.** If `adb connect` says "No route to host" while the port answers, restart the adb server.
- **Disruption.** Installing a build stops whatever is playing on the phone.
